## 1. Зачем это делается

Набор рос вместе с рефакторингом слоёв и накопил три вида избыточности.

**Параметризация по файлам.** 51 архитектурная функция разворачивается в
427 тестовых идентификаторов: каждое правило прогоняется отдельным тестом
на каждый файл пакета. Добавление файла в `src/services` механически
добавляет два десятка «тестов», хотя проверяемых правил не прибавилось.
Отчёт при этом хуже: падает первый попавшийся файл, остальные нарушения
не видны до следующего прогона.

**Один случай — один тест.** Правило «чужой или отсутствующий объект
отвечает одинаковым 404» проверяется отдельным тестом на каждый ресурс,
каждый сервис и каждый маршрут. Это одно правило, и оно должно
проверяться один раз по всему списку ресурсов, показывая сразу все
исключения.

**Дублирование по слоям.** Одно и то же поведение закреплено юнит-тестом
с моками, api-тестом и characterization-тестом. Юнит-тест с моками при
этом чаще фиксирует хореографию вызовов, а не результат: он падает при
безобидном рефакторинге и молчит при настоящей ошибке.

## 2. Принципы отбора

Тест остаётся, если верно хотя бы одно:

- он закрепляет **контракт**: URL, метод, статус, форму ответа, формат
  MCP-инструмента, правило прав, границу транзакции;
- он покрывает **нетривиальный алгоритм**: расчёт позиций и уплотнение,
  выделение цикла в ИСР, чанкинг, backoff и повторные попытки, перенос
  дат, дедупликация очереди;
- он ловит **регрессию, которую больше никто не поймает**: архитектурный
  guard, поведение на реальном PostgreSQL, компенсация внешнего файла.

Тест сворачивается или удаляется, если верно хотя бы одно:

- он проверяет, что сервис вызвал репозиторий с такими-то аргументами,
  при том что результат уже закреплён api- или integration-тестом;
- он отличается от соседнего теста одним значением параметра — такие
  случаи собираются в один табличный тест со списком всех нарушений;
- он повторяет уже закреплённое на другом слое, не добавляя ни одного
  нового утверждения о поведении.

**Запрещено** снижать покрытие ниже 78% и удалять последний тест любого
пункта Definition of Done из плана рефакторинга. Каждое удаление
обосновывается в коммите: где это поведение проверяется теперь.

## 3. Форма, к которой приводится набор

Правило вместо перечисления: один тест разбирает всё дерево и
утверждает пустоту списка нарушений.

```python
def test_service_never_reads_global_settings() -> None:
    offenders = [
        f"{path.relative_to(SRC.parent)}:{line}"
        for path in iter_python_files("services")
        for line in calls_named(ast.parse(path.read_text("utf-8")), "get_settings")
    ]
    assert not offenders, "get_settings() в сервисах: " + ", ".join(offenders)
```

Такой тест один, а сообщение содержит все нарушения сразу, а не первое.

Сценарий вместо цепочки микротестов: там, где пять тестов по очереди
дёргают один и тот же use case и проверяют по одному полю, остаётся один
тест, проходящий сценарий целиком и утверждающий все его следствия.

### Этап 2. Матрицы прав в api

`tests/api/test_write_scope_enforcement.py` (46) и

`tests/unit/knowledge/**` (68), `tests/unit/mcp_server/**` (70),

### Этап 5. Integration на PostgreSQL

`tests/integration/**` (108). Ценность этих тестов максимальна: они

Финал: полный прогон, сверка покрытия, запись принципов отбора в

## 4а. Где сокращение остановилось

Цель была 4–5 раз, фактический результат — 2,8. Разница целиком приходится
на три группы тестов, объединение которых пробовалось и было откачено.

**Integration на PostgreSQL (90 тестов).** Сценарии видят строки друг
друга: объединённые проверки очереди знаний и календаря задач начали
считать чужие записи (`assert [9] == [11]`, `{14, 16, 17, 18, 19} == {18, 19}`).
Изоляция здесь и есть предмет проверки — эти тесты единственные
подтверждают транзакции, каскады и конкурентный захват.

**Жизненный цикл приложения (`unit/test_main.py`).** Тесты взводят
события остановки и снимают задачи воркера; во втором сценарии одного
теста событие уже взведено, и проверка теряет смысл.

**Параметризация, где случай самостоятелен.** Отображение статусов HTTP
на решение о повторе, разбор некорректных ключей задачи — там значение
и есть проверяемая единица; свёрнутый прогон по списку сохранён там, где
правило одно, и оставлен параметризованным там, где случаи разные.

Дальнейшее сокращение возможно только слиянием несвязанных проверок в
один тест. Это уменьшило бы число, но не набор: падение перестало бы
называть, что именно сломалось. Договорённость плана — брать качеством,
поэтому счёт остановлен на 457.
