# Временная карта проекта

> Статус: финальное техническое задание и план реализации. Дата
> фиксации: 2026-09-02.

## 1. Краткая идея

В проекте предлагается создать вкладку **«Календарь»**, центральным
представлением которой станет **«Временная карта проекта»**.

Это не только сетка с дедлайнами. Экран должен соединить календарь,
roadmap, структуру работ, загрузку команды и безопасное моделирование
изменений. Пользователь видит не просто дату задачи, а её место во
времени, связь с этапом и ИСР, причины риска и возможные последствия
переноса.

Ключевой принцип:

> Календарь показывает факты. Временная карта объясняет состояние
> проекта и позволяет проверить сценарий до изменения данных.

Навигационное название остаётся простым --- **«Календарь»**. Название
«Временная карта» используется внутри экрана и в продуктовой
коммуникации.

## 2. Что представляет собой существующий проект

Project Task Tracker Vera --- проектно-ориентированный трекер. Проект
является корневой сущностью, а задачи, стадии, документы, ИСР,
статистика и AI-контекст существуют только внутри него.

### 2.4. Каких данных пока нет

-   даты начала отдельной задачи;
-   продолжительности и оценки трудозатрат;
-   зависимостей между задачами;
-   формальных milestones;
-   зафиксированного baseline-плана;
-   календаря доступности и загрузки участника;
-   связи `assignee` с реальным участником проекта;
-   времени фактического завершения задачи;
-   сохранённых сценариев «что, если».

Следствие: первая версия может честно показывать дедлайны, их плотность,
просрочки и историю переносов. Критический путь, прогноз завершения и
загрузку в часах нельзя достоверно вычислять до расширения модели.

## 3. Продуктовые принципы календаря

1.  **Одна Task во всех представлениях.** Календарь не создаёт отдельные
    календарные задачи. Это те же сущности, что на канбане, в списке и
    ИСР.
2.  **Факт отделён от прогноза.** Сохранённые даты, вычисленный риск и
    AI-предложение визуально различаются.
3.  **Причина видна рядом с сигналом.** Красная подсветка без объяснения
    не допускается.
4.  **Изменения подтверждает человек.** Агент и режим сценария не меняют
    сроки молча.
5.  **Постепенное раскрытие сложности.** Обычный пользователь начинает с
    календаря; roadmap, загрузка и зависимости доступны как режимы того
    же экрана.
6.  **Проект остаётся границей данных.** Запросы, фильтры, сценарии и
    источники всегда ограничены текущим проектом.
7.  **Календарь работает без AI-провайдеров.** Основной временной контур
    полностью детерминирован и хранится в PostgreSQL.

## 4. Место в интерфейсе

Предлагаемый маршрут:

``` text
/projects/:projectKey/calendar
```

Предлагаемый порядок вкладок:

``` text
Обзор · Канбан · Задачи · Календарь · Структура · Документы · AI-вики
```

Task Drawer остаётся общим и открывается поверх календаря через
существующий `selectedTaskId` в Zustand. Переход между вкладками не
создаёт вторую карточку задачи и не меняет модель навигации.

## 5. Устройство экрана

``` text
┌─────────────────────────────────────────────────────────────────────────────┐
│ Календарь  [Сегодня]  ‹ Сентябрь 2026 ›  [Месяц ▾] [По ИСР ▾] [Сценарий] │
│ Фильтры: [Стадия] [Исполнитель] [Приоритет] [Только риски]       [Поиск]   │
├───────────────────────────────────────────────────────────┬─────────────────┤
│                  временной холст                           │ Пульс проекта   │
│ Пн       Вт       Ср       Чт       Пт       Сб       Вс  │                 │
│          1        2        3        4        5        6   │ 3 просрочено   │
│                   TEST-12           ◆ Спецификация         │ 7 близких      │
│                                                           │ 4 без срока    │
│ 7        8        9        10       11       12       13  │                 │
│ TEST-21                    TEST-4                           │ Причины риска  │
│                            СЕГОДНЯ                         │ ...             │
├───────────────────────────────────────────────────────────┴─────────────────┤
│ Ближайшие дедлайны · Без срока · Недавние переносы                           │
└─────────────────────────────────────────────────────────────────────────────┘
```

Основные области:

-   **toolbar** --- дата, масштаб, группировка и режим сценария;
-   **временной холст** --- календарная сетка или временная шкала;
-   **«Пульс проекта»** --- агрегаты и объяснимые сигналы риска;
-   **нижняя/боковая agenda** --- ближайшие дедлайны, задачи без срока и
    переносы;
-   **Task Drawer** --- просмотр и редактирование выбранной задачи.

На широком экране «Пульс проекта» располагается справа. На узком он
становится сворачиваемой секцией под календарём, а Task Drawer
превращается в полноэкранную панель согласно действующему дизайн-гайду.

## 6. Режимы временной карты

### 6.1. Месяц

Первый и самый понятный режим:

-   задачи размещаются в дне своего `due_date`;
-   завершённые задачи остаются видимыми, но приглушёнными;
-   просроченные и близкие сроки отличаются тоном и иконкой, а не только
    цветом;
-   project deadline отображается как отдельный marker;
-   переполнение дня сворачивается в `+N`, открывающее agenda дня;
-   задачи без срока находятся в отдельной управляемой очереди.

### 6.2. Неделя

Рабочая шкала по дням без почасовых слотов. Проект сейчас хранит `date`,
а не время и timezone, поэтому имитация календаря встреч была бы ложной
точностью.

Режим показывает:

-   ближайшие дедлайны;
-   плотность работы по дням;
-   задачи, которые входят в неделю без назначенного исполнителя или
    срока;
-   изменения сроков за выбранный период.

### 6.3. Roadmap: месяц / квартал

После появления `Task.start_date` задача превращается из точки в полосу.
Строки можно группировать:

-   по ИСР;
-   по стадии;
-   по исполнителю;
-   по ответственным ролям.

Масштаб меняется без перехода на другой экран. Координата по горизонтали
всегда выводится из даты, а не сохраняется в БД.

### 6.4. Загрузка команды

Режим появляется только после связи задачи с участником и появления
оценки трудозатрат. Он показывает плановую нагрузку по неделям,
свободные окна и превышение доступной ёмкости.

Количество задач само по себе не считается загрузкой: одна задача может
занимать час, другая --- две недели.

### 6.5. История плана

Поверх текущих сроков включается слой изменений:

-   предыдущий срок отображается тонким ghost-marker;
-   линия соединяет прошлый и текущий дедлайн;
-   tooltip показывает дату изменения и величину сдвига;
-   агрегат «дрейф плана» отделяется от текущей просрочки.

Существующий `TaskActivity.DUE_DATE_CHANGED` позволяет показать
последующие переносы. Для надёжного сравнения с первоначальным планом
потребуется явный baseline: история не гарантирует наличие
первоначального срока задачи.

## 7. Визуальный язык

Календарь продолжает действующий стиль «VS Code / Linear для управления
проектами»:

-   фон и поверхности берутся из `bg-app`, `bg-surface`, `bg-surface-2`;
-   границы --- из `line`, `line-subtle`, `line-strong`;
-   текст --- `primary`, `secondary`, `muted`;
-   акцент, success, warning и danger --- только из общих токенов;
-   радиусы, тени и длительности анимаций --- из `frontend/src/app.css`;
-   локальные HEX и новая независимая палитра не вводятся.

Семантика задачи:

  -----------------------------------------------------------------------
  Состояние                           Представление
  ----------------------------------- -----------------------------------
  Обычный будущий срок                спокойная компактная плашка

  Срок близко                         warning-маркер и текстовая
                                      подсказка

  Просрочено                          danger-маркер, подпись «просрочено
                                      N дней»

  Завершено                           приглушённая плашка с иконкой
                                      завершения

  Выбрано                             accent-border и связь с Task Drawer

  Предлагаемое изменение              полупрозрачный ghost, пунктир и
                                      подпись сценария

  Конфликт                            отдельная иконка и объяснение
                                      причины
  -----------------------------------------------------------------------

Фон временной сетки может показывать тепловую карту плотности, но не
должен окрашивать каждую карточку. Состояние никогда не передаётся одним
цветом.

## 8. Основные взаимодействия

### 8.1. Просмотр

-   клик по задаче открывает существующий Task Drawer;
-   клик по дню открывает agenda этого дня;
-   наведение показывает ключ, название, стадию, исполнителя и причину
    подсветки;
-   фильтры и выбранный диапазон отражаются в query string, чтобы
    ссылкой можно было поделиться;
-   «Сегодня» возвращает временной фокус без сброса фильтров.

### 8.2. Перенос срока

В обычном режиме перенос задачи на другой день вызывает существующий
сценарий обновления Task и создаёт `DUE_DATE_CHANGED`.

Перед сохранением интерфейс показывает:

-   старую и новую дату;
-   величину сдвига;
-   известные последствия;
-   подтверждение для изменений, затрагивающих зависимости.

Drag-and-drop не является единственным способом: та же операция доступна
через клавиатуру и диалог выбора даты.

### 8.3. Режим сценария

В режиме «Что, если» изменения сначала живут как локальный overlay:

1.  пользователь переносит одну или несколько задач;
2.  система пересчитывает детерминированные последствия;
3.  текущий план и предлагаемый план видны одновременно;
4.  справа появляется список всех изменений и предупреждений;
5.  пользователь отменяет сценарий или применяет его одной
    подтверждённой операцией.

До подтверждения PostgreSQL не меняется. Первую версию сценария не нужно
хранить на сервере. Совместное сохранение и обсуждение сценариев может
стать отдельной последующей функцией.

## 9. «Технологичные» функции без магии

### 9.1. Пульс проекта

Начальный риск рассчитывается детерминированно и объяснимо:

-   срок уже прошёл, а стадия не завершающая;
-   срок попадает в ближайшее окно;
-   у задачи нет срока;
-   у задачи нет исполнителя;
-   дедлайн проекта приближается при наличии незавершённых задач;
-   срок переносился несколько раз.

После появления зависимостей и трудозатрат добавляются:

-   незавершённый или просроченный predecessor;
-   отрицательный временной резерв;
-   превышение недельной ёмкости исполнителя;
-   цепочка, сдвигающая milestone или срок проекта.

Результат должен возвращать не только уровень, но и reason codes,
например:

``` json
{
  "level": "high",
  "reasons": [
    { "code": "OVERDUE", "days": 4 },
    { "code": "BLOCKED_SUCCESSOR", "task_key": "TEST-42" }
  ]
}
```

Это позволяет одинаково объяснять риск в UI, API, MCP и Project Agent.

### 9.2. Волна последствий

При переносе задачи система проходит только по графу её successors и
строит preview:

-   какие задачи конфликтуют с новым сроком;
-   какие milestones оказываются под угрозой;
-   где появляется отрицательный резерв;
-   какие участники получают перегруженную неделю.

Расчёт выполняет доменный сервис, а не LLM. Один и тот же результат
используют UI и агент.

### 9.3. Project Agent как аналитик календаря

Примеры запросов:

-   «Что может сорвать релиз в сентябре?»
-   «Почему следующая неделя подсвечена красным?»
-   «Покажи дедлайны без ответственного».
-   «Что изменится, если перенести TEST-42 на пять дней?»
-   «Предложи варианты разгрузки недели».

Агент получает ограниченный SQL-срез и результаты детерминированных
calendar tools. Он объясняет и предлагает, но не рассчитывает граф
зависимостей из текста и не применяет изменения без явного подтверждения
пользователя.

Основной календарь не зависит от LLM, embeddings или Qdrant. Оперативные
даты остаются в PostgreSQL и не становятся источником истины в
семантическом индексе.

## 10. Развитие модели данных

### 10.1. Первая версия без расширения Task

Для read-only календаря достаточно текущих полей:

-   `Task.due_date`;
-   `Task.stage_id`;
-   `Task.priority`;
-   `Task.assignee`;
-   `Task.wbs_node_id`;
-   `Project.start_date` и `Project.due_date`.

Нужен только эффективный запрос по диапазону и индекс для него.
Отдельную таблицу календарных событий создавать не требуется.

### 10.2. Полосы времени и baseline

Предлагаемые поля Task:

  -----------------------------------------------------------------------
  Поле                    Тип                     Назначение
  ----------------------- ----------------------- -----------------------
  `start_date`            `date`, nullable        плановое начало полосы

  `baseline_start_date`   `date`, nullable        утверждённое исходное
                                                  начало

  `baseline_due_date`     `date`, nullable        утверждённый исходный
                                                  дедлайн

  `estimate_minutes`      `integer`, nullable,    плановая трудоёмкость
                          `> 0`                   без ошибок float

  `completed_at`          timezone-aware          фактическое завершение
                          datetime, nullable      

  `assignee_user_id`      FK, nullable            связь с реальным
                                                  участником проекта
  -----------------------------------------------------------------------

Инварианты сервисного слоя:

-   `start_date <= due_date`, когда обе даты заданы;
-   связанный исполнитель является участником того же проекта;
-   `completed_at` согласуется с переходом в завершающую стадию;
-   изменение baseline выполняется отдельным явным сценарием, а не
    обычным drag-and-drop.

Свободный `assignee` нельзя удалять одной миграцией: сначала требуется
стратегия совместимости и переноса существующих подписей.

### 10.3. Зависимости

Отдельная таблица `task_dependencies`:

``` text
id
project_id
predecessor_task_id
successor_task_id
dependency_type
lag_days
created_at
```

Начальная семантика может быть ограничена типом finish-to-start.
Требования:

-   обе задачи принадлежат одному проекту;
-   задача не зависит сама от себя;
-   пара predecessor/successor уникальна;
-   добавление связи не создаёт цикл;
-   удаление задачи каскадно удаляет её связи;
-   доступ проверяется через участие в проекте.

### 10.4. Milestones

Milestone лучше моделировать отдельной сущностью, а не специальной
задачей с фиктивной стадией:

``` text
ProjectMilestone
├── project_id
├── title
├── due_date
├── status
├── wbs_node_id (nullable)
└── description_md (nullable)
```

Дедлайн самого проекта отображается как системный milestone и не
дублируется отдельной строкой.

### 10.5. Ёмкость команды

Расчёт загрузки требует как минимум:

-   связанного участника;
-   `estimate_minutes`;
-   доступной ёмкости участника по неделе;
-   правил нерабочих дней.

До появления этих данных UI не должен подменять трудоёмкость количеством
карточек.

Все изменения схемы оформляются отдельными Alembic-миграциями.
PostgreSQL остаётся source of truth.

## 11. Предлагаемый API

### 11.1. Чтение диапазона

``` http
GET /api/v1/projects/{project_id}/calendar
    ?date_from=2026-09-01
    &date_to=2026-09-30
    &stage_id=2
    &priority=HIGH
    &assignee=Иван
    &wbs_node_id=17
```

Ответ --- компактная read model, а не полные карточки задач:

``` json
{
  "range": { "date_from": "2026-09-01", "date_to": "2026-09-30" },
  "project": {
    "start_date": "2026-08-15",
    "due_date": "2026-10-01"
  },
  "tasks": [
    {
      "id": 42,
      "key": "TEST-42",
      "title": "Подготовить спецификацию",
      "start_date": null,
      "due_date": "2026-09-12",
      "stage_id": 2,
      "wbs_node_id": 17,
      "priority": "HIGH",
      "assignee": "Иван",
      "is_done": false,
      "updated_at": "2026-09-02T12:00:00Z"
    }
  ],
  "summary": {
    "overdue": 3,
    "due_soon": 7,
    "unscheduled": 4
  }
}
```

Ограничения контракта:

-   диапазон обязателен и ограничен сервером разумным максимальным
    окном;
-   возвращаются задачи, чьи сроки попадают в окно; после появления
    `start_date` --- задачи, чей интервал пересекает окно;
-   задачи без срока не примешиваются неограниченным массивом к каждому
    месяцу;
-   сервер возвращает date-only значения как `YYYY-MM-DD` без
    искусственного timezone.

### 11.2. Задачи без срока

``` http
GET /api/v1/projects/{project_id}/calendar/unscheduled?cursor=...&limit=50
```

Отдельная пагинация не позволяет большому backlog раздувать каждый
календарный ответ.

### 11.3. Одиночное изменение

Первая версия повторно использует существующий endpoint:

``` http
PATCH /api/v1/tasks/{task_id}
{
  "due_date": "2026-09-18"
}
```

Так сохраняются существующие инварианты, история `DUE_DATE_CHANGED`,
транзакция и инвалидация связанных представлений.

### 11.4. Preview и применение сценария

После появления зависимостей:

``` http
POST /api/v1/projects/{project_id}/calendar/scenarios/preview
POST /api/v1/projects/{project_id}/calendar/scenarios/apply
```

`preview` не меняет состояние и возвращает нормализованный список
изменений, конфликты и причины риска. `apply` принимает тот же список и
ожидаемые `updated_at`, повторно валидирует сценарий и применяет
изменения одной транзакцией через Unit of Work. Если задачи изменились
после preview, сервер возвращает конфликт вместо частичного применения.

## 12. Backend-реализация

### 12.1. Слои

``` text
calendar endpoint
    ↓
CalendarService
    ├── ProjectsRepository
    ├── TasksRepository.get_calendar_range(...)
    ├── ProjectStagesRepository
    ├── WbsNodesRepository
    └── позднее: TaskDependenciesRepository / MilestonesRepository
```

-   endpoint описывает HTTP-контракт, получает доступный проект через
    Depends и мапит доменные ошибки;
-   service собирает read model, проверяет диапазон и рассчитывает
    объяснимые сигналы;
-   каждый repository выполняет запросы только своего домена;
-   SQL не формируется в endpoint или service;
-   доступ к чужому проекту возвращает 404 в соответствии с действующим
    правилом безопасности.

### 12.2. Запросы и индексы

Для первой версии нужен repository-метод с фильтрацией в PostgreSQL, а
не загрузка всех задач проекта с последующим `filter()` в Python.

Минимальный индекс:

``` text
tasks(project_id, due_date)
```

Он добавляется Alembic-миграцией и проверяется интеграционным тестом на
реальном PostgreSQL. После появления `start_date` план запроса
пересматривается по `EXPLAIN ANALYZE`; индекс не выбирается
предположительно без измерений.

Агрегаты большого проекта считаются SQL-запросами. Размер ответа
ограничивается диапазоном, а список задач без даты пагинируется
отдельно.

### 12.3. Даты

`due_date` и `start_date` --- календарные даты, не моменты времени.
Backend принимает и возвращает `date`; frontend должен разбирать
`YYYY-MM-DD` как локальные компоненты года, месяца и дня, а не как UTC
timestamp.

Это особенно важно для календаря: преобразование date-only строки через
неявный timezone может перенести задачу на соседний день у части
пользователей.

### 12.4. Вычисления

Раскладка по дням, плотность видимого диапазона и простые UI-группировки
являются derived state frontend. Бизнес-сигналы, зависимости и preview
сценария рассчитываются backend-сервисом, чтобы UI, MCP и Project Agent
получали одинаковый результат.

## 13. Frontend-реализация

### 13.1. Предлагаемая структура

``` text
frontend/src/
├── routes/ProjectCalendarPage.tsx
├── components/calendar/
│   ├── CalendarToolbar.tsx
│   ├── CalendarGrid.tsx
│   ├── CalendarDay.tsx
│   ├── CalendarTask.tsx
│   ├── CalendarAgenda.tsx
│   ├── ProjectPulse.tsx
│   ├── TimelineGrid.tsx
│   └── ScenarioPanel.tsx
└── lib/
    ├── calendar.ts
    └── dates.ts
```

Компоненты делятся по ответственности; вычисление календарной матрицы,
пересечения диапазонов и risk tones остаётся в чистых функциях
`lib/calendar.ts`, которые легко тестировать без DOM.

### 13.2. Разделение состояния

**Server state --- TanStack Query:**

-   данные выбранного диапазона;
-   задачи без срока;
-   стадии, ИСР и серверные risk reasons;
-   отдельный query key с проектом, диапазоном и фильтрами.

**Derived state:**

-   дни видимой сетки;
-   группировка задач;
-   координаты полос;
-   число скрытых элементов дня;
-   локальное представление heatmap.

**UI state:**

-   масштаб и группировка;
-   открытая agenda;
-   временные изменения сценария;
-   выделение задачи;
-   состояние боковой панели.

Стабильные параметры вида хранятся в URL. Краткоживущий draft сценария
можно держать локально; переносить всё календарное состояние в
глобальный Zustand не требуется.

### 13.3. Повторное использование технологий

Первый календарь можно реализовать без новой зависимости:

-   CSS Grid и sticky positioning --- сетка и заголовки;
-   TanStack Query --- загрузка, кэш и инвалидация диапазонов;
-   `@dnd-kit` --- перенос дедлайнов с pointer и keyboard interaction;
-   `react-aria-components` --- доступные menu, popover, dialog и выбор
    режима;
-   существующие `Button`, `Badge`, `DueDate`, `Drawer`, `Skeleton`,
    `EmptyState`, `ErrorMessage`;
-   `lucide-react` --- единый набор иконок;
-   общие Tailwind-токены --- визуальный стиль.

`@xyflow/react` остаётся технологией ИСР. Использовать графовый canvas
как основу календаря не следует: временная координата детерминирована
датой, а не layout-алгоритмом. Связи зависимостей в roadmap можно позже
рисовать отдельным SVG-overlay над временной сеткой.

Виртуализация строк и тяжёлая canvas-отрисовка вводятся только после
профилирования на реальном количестве задач. Месячная сетка не должна
получать сложность большого Gantt заранее.

### 13.4. Инвалидация данных

После изменения даты должны согласованно обновляться:

-   текущий диапазон календаря;
-   список задач и конкретная задача;
-   канбан;
-   статистика проекта;
-   общий dashboard;
-   agenda задач без срока;
-   при необходимости структура, если она показывает дедлайн.

Оптимистичное обновление допустимо для одиночного переноса с
обязательным rollback и toast при отказе. Пакетный сценарий применяется
только после серверного preview и транзакционного подтверждения.

## 14. Доступность и адаптивность

-   каждый drag-сценарий имеет кнопку/диалог как альтернативу;
-   календарная сетка использует семантические подписи дней и доступные
    названия задач;
-   focus-visible следует общей дизайн-системе;
-   стрелки перемещают фокус предсказуемо, `Enter` открывает задачу;
-   причина риска доступна текстом;
-   `prefers-reduced-motion` отключает декоративные переходы;
-   weekend не отличается только цветом;
-   на мобильном месячная сетка превращается в agenda по дням, а не
    сжимается до нечитаемого состояния.

## 15. Безопасность и целостность

-   все calendar endpoints используют существующую проверку участия в
    проекте;
-   клиент не передаёт доверенный `project_id` для задачи ---
    принадлежность проверяет сервис;
-   зависимости разрешены только внутри одного проекта;
-   preview не обладает правом записи;
-   apply повторно валидирует доступ и версии всех изменяемых задач;
-   агент не получает обходной канал записи в БД;
-   календарь не переносит оперативные даты в Qdrant как источник
    истины;
-   основная вкладка продолжает работать при недоступности Qdrant,
    embedding API или LLM.

## 16. Наблюдаемость

Структурные backend-логи должны фиксировать:

-   `project_id`, диапазон и число возвращённых задач;
-   длительность SQL и сборки read model;
-   число предупреждений по уровням без пользовательского текста;
-   длительность preview;
-   число изменений и конфликтов при apply.

Для UI полезно измерять время до первой отрисовки диапазона и число
показанных элементов. Значения performance budget следует установить
после замера на репрезентативном проекте, а не придумывать заранее.

## 21. Целевой результат

Пользователь открывает проект и за несколько секунд понимает:

-   какие сроки наступают;
-   где сконцентрирован риск;
-   почему задача или период подсвечены;
-   какие элементы проекта связаны с риском;
-   что произойдёт при переносе;
-   какие изменения предлагаются и какие из них будут применены.

Экран остаётся быстрым рабочим инструментом в стиле существующего
приложения. Технологичность выражается не в декоративной сложности, а в
единой модели времени, объяснимых вычислениях, безопасном preview и
связи календаря с задачами, ИСР, документами и Project Agent.

## 22. Зафиксированные решения для реализации

Этот раздел имеет приоритет над открытыми вопросами и вариантами,
описанными выше.

### 22.1. Единый временной workspace

Не создавать три независимых продукта `Calendar`, `Gantt` и `Roadmap`.

Вкладка проекта называется **«Календарь»**, а внутри используется единая
**«Временная карта проекта»** с масштабами:

``` text
Неделя | Месяц | Квартал
```

-   неделя --- детальное представление;
-   месяц --- основной рабочий режим;
-   квартал --- высокоуровневый roadmap.

Масштаб меняет визуальную детализацию, но не модель данных.

### 22.2. Связь с ИСР

После появления `Task.start_date` основное Timeline-представление
строится совместно с существующей ИСР:

``` text
                              SEPTEMBER                 OCTOBER
                        1     8    15    22    29     6    13

▼ 1 Backend
  ▼ 1.1 API
      TASK-12           █████████
      TASK-14                 █████████████
  ▶ 1.2 Database             █████████████████

▼ 2 Frontend
  ▼ 2.1 Auth
      TASK-24                            █████████████
```

ИСР отвечает на вопрос «где находится работа в структуре», временная
карта --- «где эта же работа находится во времени».

Ветки ИСР поддерживают collapse/expand. Свёрнутый узел показывает
компактный агрегат:

``` text
▶ Backend · 8 задач · 63% · 2 риска
```

### 22.3. Semantic zoom

Чем крупнее временной масштаб, тем меньше вторичных данных показывается.

Детальный уровень:

``` text
TASK-142
Реализовать авторизацию
HIGH · In Progress
08–15 Sep
```

Средний:

``` text
TASK-142 · Авторизация
```

Квартальный:

``` text
Backend · 12 задач · 67%
```

`ProjectMilestone` остаётся отдельной простой сущностью.

Не добавлять milestone собственный Kanban workflow, assignee или
отдельную сложную жизненную модель.

`Project.due_date` отображается как системный milestone и не дублируется
записью.

### 22.5. Dependencies

Первая версия зависимостей поддерживает **только Finish-to-Start**.

Не реализовывать Start-to-Start, Finish-to-Finish и Start-to-Finish до
появления доказанной продуктовой необходимости.

### 22.6. Workload

Режим реальной загрузки команды не входит в первую целевую версию.

Он может появиться только после наличия:

-   связанного участника проекта;
-   оценки трудоёмкости;
-   модели доступной ёмкости;
-   правил рабочего календаря.

Количество задач не используется как псевдометрика загрузки.

### 22.7. What-if

Режим сценария является одной из целевых возможностей, но реализуется
после стабильного Timeline, milestones, baseline и зависимостей.

До `Apply` изменения существуют только как proposed overlay и не
изменяют PostgreSQL.

### 22.8. AI

Project Agent не рассчитывает расписание, зависимости или риски
самостоятельно.

Принцип:

> Backend рассчитывает --- агент объясняет.

# 29. Технические уточнения в контексте текущей кодовой базы

Раздел дополняет спецификацию стыками с тем, что появилось в проекте
после её написания: транзакционным outbox базы знаний, MCP-слоем и
исправлениями индексации. Он не заменяет разделы 10–13, а снимает
конкретные ловушки реализации.

## 29.1. Что календарь индексирует в базе знаний, а что нет

`TASK_SEMANTIC_FIELDS` в `services/tasks.py` содержит ровно `title` и
`description_md`. Новые календарные поля — `start_date`,
`baseline_start_date`, `baseline_due_date`, `estimate_minutes`,
`completed_at`, `assignee_user_id` — **в этот набор добавлять нельзя**.

Причина не стилистическая: любое поле в этом наборе запускает
переиндексацию задачи. Перенос срока мышью стал бы вызовом embeddings
API, а это ровно то, что запрещено в § 6 концепции базы знаний и что
уже чинили точечной переиндексацией ИСР. Календарные поля операционные:
агент читает их из PostgreSQL через structured tools.

**Milestone — отдельное решение.** У него есть `title` и
`description_md`, то есть содержательный текст, по которому естественно
спрашивать «что мы решили по вехе X». Варианты:

- добавить `KnowledgeEntityType.MILESTONE` с builder и событиями —
  архитектура это допускает, новый тип не ломает существующие;
- не индексировать, агент узнаёт о вехах только структурно.

Рекомендуется первый: веха без описания бесполезна, а с описанием она
такой же носитель решений, как документ.

`task_dependencies` — чистая структура без текста, индексировать нечего.

## 29.2. Новые сервисы обязаны коммитить через UnitOfWork

В проекте введён transactional outbox: `enqueue` делает `flush`, а
транзакцию закрывает `UnitOfWork` на уровне сервиса. `CalendarService`,
`MilestonesService` и `TaskDependenciesService` обязаны следовать той же
схеме.

Если новый сервис закоммитит сам, вернётся ровно та ошибка, которую
устраняли: доменное изменение зафиксировано, задание индексации — нет,
расхождение молчаливое. Правило действует и для сервисов, которые ничего
не индексируют: граница транзакции в сценарии должна быть одна.

## 29.3. История переносов — это TaskActivity, а не новый журнал

`TaskActivityEventType` уже содержит `DUE_DATE_CHANGED`, а
`TasksService._record_field_changes` пишет события при обновлении задачи.
Режим «История плана» (§ 6.5) должен читать этот источник.

Для новых полей добавляются значения перечисления — `START_DATE_CHANGED`
и `BASELINE_CHANGED` — и обработка в том же методе. Отдельная таблица
календарной истории создала бы второй источник правды об одном и том же
событии, и они разойдутся при первой же операции, выполненной не через
календарь.

## 29.4. Одно определение «просрочено» на всё приложение

Сейчас предикат живёт в двух местах:

- SQL-агрегат в `repositories/tasks.py`: фильтр
  `ProjectStage.is_done_stage IS FALSE AND Task.due_date < today`;
- Python в `services/dashboard.py`: та же логика выражением над моделью.

Календарь станет третьим местом, а его сигналы видны пользователю рядом
с цифрами дашборда. Расхождение заметят сразу: «просрочено 4» на
дашборде и три красные задачи в календаре — это баг доверия, а не
косметика.

Предикат нужно вынести в одно место и переиспользовать во всех трёх
контурах до того, как появится третья копия.

## 29.5. Чей «сегодня»

`date.today()` в `dashboard.py` и `projects.py` возвращает дату в часовом
поясе **сервера**. Для счётчика на дашборде это терпимо, для календаря —
нет: у пользователя в другом поясе подсветится не тот день, а задача со
сроком сегодня покажется просроченной.

Два решения:

1. клиент передаёт свою текущую дату в запрос диапазона, сервер считает
   сигналы относительно неё;
2. сервер отдаёт только факты (`due_date`, `is_done_stage`), а
   «просрочено» и «сегодня» вычисляет frontend.

Второй проще и согласуется с § 12.4: раскладка и подсветка — derived
state клиента. Но тогда правило из 29.4 нужно применить и к frontend,
иначе третья копия предиката появится в TypeScript.

## 29.6. Конкретная стратегия для assignee_user_id

Спецификация верно требует стратегию совместимости (§ 10.2). Предлагается:

1. добавить nullable `assignee_user_id`, **не удаляя** текстовый
   `assignee`;
2. одноразовый скрипт сопоставления по ФИО участников проекта — с
   отчётом и без автоматической привязки неоднозначных совпадений;
3. UI при выборе участника заполняет оба поля: связь для расчётов,
   подпись для отображения;
4. текстовое поле остаётся для внешних исполнителей, которых нет в
   системе как пользователей.

Удаление `assignee` — отдельное решение после того, как загрузка команды
реально заработает, а не часть этой миграции.

## 29.7. Где заполнять completed_at

Единственная точка перехода в завершающую стадию —
`TasksService.move_task`, там же уже пишется `STAGE_CHANGED`. Заполнение
и сброс `completed_at` должны жить там.

Триггер на уровне БД не подходит: значение разойдётся с историей задачи,
которую пишет сервис. Возврат из завершающей стадии обязан сбрасывать
поле в `NULL`, иначе «фактическое завершение» останется у незавершённой
задачи.

## 29.8. MCP: календарь наружу

MCP-слой готов и работает: 12 инструментов, контракт на отображаемых
ключах, скоупы `READ`/`WRITE`. Итерация 8 конкретизируется так:

| Инструмент | Scope | Назначение |
|---|---|---|
| `get_calendar_range` | read | задачи и вехи в диапазоне дат |
| `list_tasks_without_due_date` | read | пул задач без срока |
| `set_task_dates` | write | проставить или сдвинуть даты задачи |
| `list_milestones` | read | вехи проекта |
| `create_milestone` | write | завести веху |

Требования те же, что у существующих инструментов: изменяющие идут через
`require_write=True`, наружу отдаются ключи `PROJ-142`, а не числовые
идентификаторы, диапазон обязан иметь предел — иначе агент запросит
десять лет одним вызовом.

Preview сценария наружу не выставлять, пока сама функция не появится и
не будет проверена в интерфейсе.

## 29.9. Ленивая загрузка маршрута

`StructurePage` вынесен в `lazy()` с `Suspense` в `App.tsx`, потому что
тянет React Flow и elkjs — около 513 КБ gzip отдельным чанком.

Календарь по § 13.3 обходится CSS Grid и уже имеющимися зависимостями,
поэтому ради размера ленивая загрузка ему не нужна. Она понадобится,
если появится timeline с SVG-overlay зависимостей и виртуализацией.
Решение принимать по профилю сборки, а не заранее.

## 29.10. Дисциплина Alembic при параллельной работе

Календарь добавит несколько миграций. Если работа идёт в отдельной ветке
одновременно с другой веткой, обе ответвятся от одной головы, и после
слияния у Alembic окажется две головы.

Конфликта в git при этом **не будет** — файлы миграций разные. Проект
уже ломался ровно так после слияния MCP-слоя: тесты остались зелёными,
а контейнер уходил в бесконечный перезапуск, потому что тесты не
выполняют `alembic upgrade head`.

Правило: после любого слияния, затронувшего миграции, прогонять
`alembic upgrade head` на чистой базе. Зелёные тесты этого класса
поломок не ловят.

## 29.11. Связь с незакрытыми задачами базы знаний

Открытым остаётся § 12 плана развития AI-вики — дедупликация по
content-hash. Он тоже трогает представление задачи в индексе.

Жёсткой очерёдности нет, но добавление полей в `Task` — подходящий
момент, чтобы зафиксировать правило из 29.1 в коде и тестах: новые поля
не входят в semantic representation. Тогда последующая работа над
хэшированием не столкнётся с задачами, которые переиндексируются от
каждого переноса срока.
