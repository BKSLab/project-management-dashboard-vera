# FastAPI — паттерны архитектуры личного трекера

Нормативный guide для backend этого приложения. Запуск и конфигурация описаны в
[README](README.md), правила работы агента — в [AGENTS.md](AGENTS.md).
Соответствие кода проверяют [архитектурные guards](backend/tests/architecture/).
Их явные реестры и исключения меняются вместе с соответствующим контрактом.

## 1. Слоистая архитектура

`HTTP / WebSocket / MCP → Service → Repository → PostgreSQL`.
Сервис также обращается к явно переданным клиентам и файловому хранилищу.

- Endpoint не импортирует SQLAlchemy, модели, репозитории или реализации LLM/Qdrant.
- Сервис не импортирует FastAPI, SQLAlchemy, `src.dependencies` и глобальную фабрику сессий.
- SQL, JOIN и агрегатные запросы принадлежат репозиториям; бизнес-инварианты — сервисам.
- MCP и workers используют те же сервисы и правила доступа, что HTTP.
- Общие перечисления задачи находятся в `schemas/enums.py`; транспорт не импортирует ORM ради enum.

## 2. Структура и сборка приложения

Код находится в `backend/src/`: `api/v1/endpoints`, `services`, `repositories`,
`schemas`, `exceptions`, `dependencies`, `clients`, `storage`, `db`.
Модули группируются по сущности или сценарию; одноимённые слои легко сопоставить.

Конструкторы репозиториев, сервисов и клиентов вызываются в composition points.
Это фабрики `dependencies/`, сборка MCP, knowledge и realtime; точный список —
`COMPOSITION_MODULES` в guards. Внутри обработчика не собирают собственный граф.
Workers получают зависимости через конструктор; MCP ToolContext не содержит сессии.

## 3. Конфигурация

Настройки типизированы в `core/settings.py`; секреты представлены `SecretStr`.
`get_settings()` вызывается только в объявленных composition points.
Сервис получает нужные настройки явно. Изменения конфигурации отражаются в `.env.example`.

## 4. Логирование

Используется проектный logger. Записываются идентификаторы, этап, длительность и причина сбоя.
Секреты и внутренние storage keys не выдаются в публичных DTO.
Логи не дублируют полные сообщения, содержимое файлов и чувствительные payload.
Внутренний traceback сохраняется через `logger.exception` или `exc_info=True`.

## 5. Lifespan и ресурсы

Общие HTTP/Qdrant/Redis-клиенты и runtimes создаются при старте и закрываются при остановке.
Потребитель получает готовый runtime через DI, а не через ленивый глобальный locator.
Клиент или storage не создаёт запасной сетевой transport, если его забыли передать.
Владелец ресурса и порядок его закрытия должны оставаться явными.

## 6. Dependency Injection

Обычная цепочка: `DbSessionDep → RepositoryDep → ServiceDep → endpoint`.
У каждой публичной `get_*` / `require_*` фабрики есть
`Annotated[Тип, Depends(фабрика)]`-алиас с суффиксом `Dep`.
Потребитель использует алиас, не повторяет `Depends` в аннотации параметра.
Обязательные зависимости не маскируются значением `None` или скрытым fallback.

Сценарий с внешним вызовом получает фабрику короткой DB-области (`scope`).
Реализация области и создание SQLAlchemy-объектов находятся в composition layer.
Сервис читает данные внутри `async with self.scope()`, выходит из области,
затем вызывает LLM/экстрактор/сеть. Сохранение результата открывает новую область.
Репозиторий и UnitOfWork одной операции используют одну сессию.
ORM-отношения, нужные после закрытия области, загружаются заранее.

## 7. Эндпоинты

Endpoint принимает и документирует параметры, вызывает сервис и переводит его ошибки в HTTP.
У маршрута сохраняются `summary`, `description`, `response_description`,
уникальный camelCase `operation_id`, `response_model` и реалистичные `responses`.
Параметры Path/Query и поля схем имеют описания и примеры; сигнатуры типизированы.
Изменение существующего API учитывает прежние URL, DTO, клиентов и обработку конфликтов.
Нельзя определять право записи только по HTTP-методу: существуют read-only POST.

## 8. Исключения — трёхслойная система

Репозиторий, клиент и storage поднимают собственные семейства ошибок.
Сервис перехватывает конкретные ошибки зависимостей и преобразует их в сервисный контракт
через `raise ... from error`. Нижний слой не импортирует ошибки сервисов.
Endpoint перехватывает сервисные ошибки, а не ClientError/StorageError/RepositoryError.
Перевод в HTTP: `HTTPException(status_code=error.status_code, detail=error.detail)`.
`detail` безопасен для клиента; `__str__` и traceback служат внутренней диагностике.
Ожидаемые not-found, forbidden, validation и conflict имеют отдельный смысл и тип.
Широкий `ApplicationError` допускается только на предусмотренной границе MCP.
Не добавляют бесполезный `except OwnError: raise`.

## 9. Сервисы и транзакции

Сервис реализует сценарий, проверяет принадлежность объектов и доменные инварианты.
Один бизнес-факт фиксируется одной UnitOfWork: изменение, история и transactional outbox.
Вложенный вызов не делает скрытый промежуточный commit.
Доменные репозитории составной операции выполняют DML/flush, финальный commit делает UoW.
Сохранившиеся самостоятельные repository-методы явно принимают `commit: bool = True`;
при участии в составной операции используется `commit=False`.
Ошибка откатывает операцию. Внешний publish выполняется после фиксации; повтор доставки
обрабатывается идемпотентно. Открытая транзакция во время сетевого ожидания не даёт атомарности.

## 10. Репозитории

Обычный публичный метод выполняет один SQL statement и не вызывает другой публичный метод.
Пакетная операция работает над набором строк, без запроса на каждую строку.
Исключения для неделимых операций и batch зафиксированы в `test_repository_contracts.py`.
После DML используют `RETURNING`, без `refresh()` и отдельного дочитывания.
Ошибки SQLAlchemy преобразуются в repository errors с откатом; известные нарушения
ограничений различаются по конкретному constraint и преобразуются в осмысленный конфликт.
Фильтрация и значения параметризуются. Счётчики считаются SQL-агрегатами, не выгрузкой всех строк.
Конкурентные операции не используют одновременно одну AsyncSession.

## 11. Модели SQLAlchemy

Используются общая `Base`, `Mapped` / `mapped_column` и существующие типы проекта.
Ограничения целостности, индексы, nullable и поведение FK описываются в модели и миграции.
Новые модели регистрируются в общем metadata. Поля имеют `doc` и `comment`.
Публичный DTO не строится из случайного `__dict__` ORM-объекта.

## 12. Pydantic-схемы

Публичный контракт описан схемами с ограничениями, `Field(description=..., examples=...)`
и примерами запроса. Для чтения ORM используется `from_attributes=True`, где это нужно.
Нормализация и проверка полей выполняются валидаторами; доменные проверки остаются в сервисе.
PATCH различает отсутствие поля и явный `null`. Сохраняются установленные форматы
списков/пагинации и optimistic-concurrency полей, а не вводится новый общий формат задним числом.

## 13. Клиенты внешних API/LLM

Клиенты получают готовый transport и конфигурацию через конструктор.
Они отвечают за протокол, ограниченные retries и валидацию ответа; сервис — за сценарий.
Системные prompts находятся в `src/prompts/`, structured output проверяется Pydantic-схемой.
Для LLM различаются транспортный сбой и невалидное содержимое; retries ограничены,
с backoff/jitter. Пределы попыток и timeout входят в вычисляемый worst-case бюджет.
Результат модели — недоверенные данные: идентификаторы и права проверяются сервисом
при применении. Правила подтверждения действий описаны в [документации агента](docs/agent.md).

## 14. Auth, доступ и долгоживущие ответы

Auth/access Depends вызывают сервис и переводят его ошибку в HTTP; сами не читают БД.
Они возвращают Principal/AccessGrant, не ORM-модель. Чужой объект скрывается ответом 404.
Права API-ключа ограничивают права его локального владельца, не расширяют доступ к объекту.
Публичные, сессионные, read-only POST и изменяющие маршруты классифицируются в guards.
Новый маршрут добавляется вместе с проверкой аутентификации, доступа и нужных scopes.

WebSocket, SSE, streaming и FileResponse не удерживают request-scoped DB-ресурсы.
Handshake/доступ выполняются в короткой области до длительной фазы; сообщение сокета
открывает свою область. Router-level зависимости также входят в граф WebSocket.
HTTP чата освобождает guard-сессию до операции сервиса.
Долгоживущий обработчик получает runtime и данные авторизации; отзыв прав учитывается
при обработке команд/heartbeat. Защищённые файлы не становятся публичными URL.

## 15. Миграции (Alembic)

Файл называется `<дата>_<время>_<смысл>.py`; metadata приложения и Alembic едины.
Одна миграция решает один согласованный смысловой объём.
Новые миграции по умолчанию schema-only: DDL без seed и скрытого backfill.
Если нужны начальные справочные данные, их создаёт отдельный идемпотентный seed после upgrade,
не затирая ручные данные и не активируя отключённые сущности.
Преобразование существующих данных требует отдельно согласованного объёма и проверок;
разрешённые миграции совместимости P не дают общего разрешения на произвольный DML.
Существующие данные и связи сохраняются в пределах согласованного upgrade/downgrade.
После изменения/слияния миграций проверяются head, применение на чистой базе и обновление
прежней схемы с данными. Деструктивный downgrade описывается явно.

## 16. Инфраструктура и запуск

Compose ждёт готовности БД через depends_on/healthcheck; entrypoint.sh применяет миграции
и запускает ASGI. Ресурсами приложения управляет lifespan; команды и настройки — в README.
Для новых синхронных вызовов бюджет проверяется по всей цепочке:
`worst-case внешнего клиента < timeout frontend HTTP < proxy_read_timeout`.
Изменение retries или timeout требует пересчёта соседних уровней.
Известное несоответствие старых синхронных AI-вызовов описано в [docs/agent.md](docs/agent.md).
Операцию, не помещающуюся в синхронный бюджет, выполняют асинхронно с ID и получением результата.
Для диагностики различают задержку upstream, ожидание пула, долгие транзакции и число сокетов.

## 17. Стиль кода и документирования

Код типизирован; русские docstrings публичных методов в Google-стиле описывают поведение,
аргументы, результат и значимые ошибки. Комментарии объясняют причину решения.
Используется существующий Ruff и форматирование проекта; мёртвые запасные реализации не сохраняются.
Повторяемые ограничения и лимиты именуются, а не прячутся в телах методов.

## 18. Тестирование

- Сервис: unit с подменой зависимостей; проверяются результат, инварианты и точный тип ошибки.
- Репозиторий: настоящий PostgreSQL в testcontainers; SQLite/мок execute не заменяют проверку SQL.
- Клиент: подмена транспорта, включая ошибки и retries; API: ASGITransport и dependency overrides.
- Scope/auth, транзакции, гонки и миграции проверяются интеграционно на изолированных данных.
- Fixture с сервисными commit изолируется внешней транзакцией и savepoint либо отдельной тестовой БД.
- Realtime проверяется с настоящим Redis; idle sockets не должны исчерпывать пул обычных запросов.
- Новые зависимости/маршруты сохраняют архитектурные guards; исключение не добавляют ради обхода сбоя.
- Консолидация не удаляет последнюю проверку контракта; порог покрытия и команды — в README.
