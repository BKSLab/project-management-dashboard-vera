# Техническое задание: интерактивный конструктор ИСР проекта

## 1. Назначение

Необходимо реализовать в существующем task tracker интерактивный модуль формирования ИСР — иерархической структуры работ проекта.

ИСР не должна быть свободным графическим редактором наподобие Figma или Miro.

От Figma/Miro необходимо взять только UX взаимодействия с рабочей областью:

- практически бесконечный canvas;
- pan;
- zoom;
- minimap;
- fit-to-screen;
- плавное перемещение по большой структуре;
- drag & drop;
- визуальное выделение выбранных объектов.

Сама структура должна оставаться строго иерархической и формироваться системой автоматически.

Пользователь управляет:

- структурными блоками;
- их иерархией;
- порядком блоков;
- распределением существующих задач по блокам.

Пользователь **не управляет координатами блоков вручную**.

---

# 2. Основная концепция

Проект содержит набор обычных Task.

Помимо задач пользователь может сформировать структуру проекта:

```text
Project
│
├── Backend
│   │
│   ├── API
│   │   ├── TASK-15
│   │   └── TASK-18
│   │
│   └── Database
│       └── TASK-23
│
├── Frontend
│   │
│   ├── Authentication
│   │   └── TASK-31
│   │
│   └── Dashboard
│       ├── TASK-35
│       └── TASK-37
│
└── Deployment
    └── TASK-41
```

Структурные элементы:

```text
Backend
API
Database
Frontend
Authentication
Dashboard
Deployment
```

не являются задачами.

Это отдельная сущность:

```text
WbsNode
```

Задача может быть прикреплена к одному WbsNode.

Если задача не прикреплена ни к одному WbsNode, она считается **нераспределённой** и отображается в пуле задач слева.

---

# 3. Ключевой архитектурный принцип

Необходимо чётко разделять:

## Task

Реальная единица работы.

Имеет существующие свойства:

- название;
- описание;
- статус;
- приоритет;
- дедлайн;
- комментарии;
- историю;
- исполнителя;
- прочие существующие поля.

## WbsNode

Структурный контейнер.

Например:

```text
Backend
Frontend
API
Testing
Deployment
```

WbsNode нужен исключительно для организации задач внутри структуры проекта.

---

# 4. Единая сущность Task во всех представлениях

Task не копируется для ИСР.

Одна задача одновременно может отображаться:

```text
Kanban
Tasks List
Dashboard
WBS / Structure
```

Это разные представления одной и той же сущности.

Например:

```text
Task:

TASK-142
Реализовать фильтрацию проектов

project_id = 14
status = in_progress
priority = high
wbs_node_id = 32
```

Kanban интерпретирует:

```text
status = in_progress
```

и показывает задачу в колонке `In Progress`.

Structure Builder интерпретирует:

```text
wbs_node_id = 32
```

и показывает её внутри соответствующего раздела ИСР.

Изменение статуса задачи в Kanban не должно менять её позицию в ИСР.

Изменение WBS-раздела не должно менять статус задачи.

# 5. Backend

Реализация должна соответствовать существующей слоистой архитектуре FastAPI и правилам проекта, установленным в `FASTAPI_PATTERNS.md`.

Необходимо использовать существующие подходы:

```text
API
↓
Service
↓
Repository
↓
SQLAlchemy
↓
PostgreSQL
```

Не размещать бизнес-логику формирования и изменения ИСР непосредственно в router.

---

# 6. Модель WbsNode

Минимальная модель:

```text
WbsNode

id
project_id
parent_id
title
position
created_at
updated_at
```

Где:

### id

Идентификатор узла.

### project_id

Проект, которому принадлежит узел.

WbsNode не может существовать вне Project.

### parent_id

Родительский WbsNode.

`NULL` означает верхний уровень структуры.

### title

Название блока.

Например:

```text
Backend
Database
API
Testing
```

### position

Порядок элемента среди элементов одного уровня.

Например:

```text
Backend      position = 1000
Frontend     position = 2000
Deployment   position = 3000
```

Рекомендуется использовать разреженную сортировку, а не `1, 2, 3`, чтобы обычное перемещение не требовало постоянно обновлять все соседние записи.

---

# 7. Связь Task с ИСР

Task должна иметь nullable-ссылку:

```text
wbs_node_id
```

или эквивалентную существующему стилю проекта связь.

```text
wbs_node_id = NULL
```

означает:

> задача существует в проекте, но ещё не распределена по ИСР.

```text
wbs_node_id = X
```

означает:

> задача относится к WbsNode X.

Task и WbsNode обязательно должны принадлежать одному Project.

Backend обязан проверять это условие.

Нельзя назначить задачу проекта A в WbsNode проекта B.

## Порядок внутри раздела

Task хранит разреженную позицию внутри своего раздела:

```text
wbs_position
```

Правило то же, что у `WbsNode.position`: значение считает backend, клиент
передаёт только соседа, перед которым встаёт задача.

```text
wbs_position = NULL
```

означает, что задача не размещена в структуре.

## Задача на холсте

Нераспределённая задача существует в двух состояниях:

```text
в списке-пуле        canvas_x = NULL, canvas_y = NULL
выложена на холст    canvas_x, canvas_y заполнены
```

Координаты холста хранятся только для задач вне структуры (см. §17). При
привязке к разделу они очищаются.

---

# 8. Нумерация ИСР

Номера:

```text
1
1.1
1.2
1.2.1
2
2.1
```

не являются постоянными данными.

Не хранить их как источник истины.

Они вычисляются из:

```text
parent_id
+
position
```

Например:

```text
Backend
    API
    Database

Frontend
```

даёт:

```text
1 Backend
1.1 API
1.2 Database
2 Frontend
```

Если пользователь поменял API и Database местами:

```text
1 Backend
1.1 Database
1.2 API
2 Frontend
```

нумерация должна измениться автоматически.

---

# 9. Ограничения структуры

Backend должен предотвращать:

- циклические зависимости;
- назначение узла самому себе как parent;
- перенос родительского узла внутрь собственного descendant;
- перенос между разными проектами;
- обращение к WbsNode другого проекта через project-scoped endpoint.

Пример запрещённой операции:

```text
Backend
└── API
```

Нельзя перенести:

```text
Backend
```

внутрь:

```text
API
```

так как получится цикл.

# 10. API

API должен быть project-scoped.

Пример:

```http
GET /projects/{project_id}/wbs
```

Получение структуры проекта.

---

```http
POST /projects/{project_id}/wbs/nodes
```

Создание структурного блока.

Пример body:

```json
{
  "title": "Backend",
  "parent_id": null
}
```

---

```http
PATCH /projects/{project_id}/wbs/nodes/{node_id}
```

Изменение:

- title;
- других редактируемых метаданных.

---

Для перемещения желательно отдельное бизнес-действие:

```http
POST /projects/{project_id}/wbs/nodes/{node_id}/move
```

Например:

```json
{
  "parent_id": "new-parent-id",
  "before_id": "node-id"
}
```

или эквивалентная модель позиционирования.

Не заставлять frontend самостоятельно вычислять внутреннюю persistence-логику сортировки.

---

Назначение задачи:

```http
POST /projects/{project_id}/wbs/tasks/{task_id}/assign
```

```json
{
  "wbs_node_id": "node-id",
  "before_task_id": null
}
```

---

Удаление из ИСР:

```http
DELETE /projects/{project_id}/wbs/tasks/{task_id}/assignment
```

При этом удаляется только связь.

**Task удаляться не должна.**

Она возвращается в пул нераспределённых задач.

---

Размещение задачи одной операцией:

```http
POST /projects/{project_id}/wbs/tasks/{task_id}/placement
```

```json
{
  "wbs_node_id": null,
  "before_task_id": null,
  "canvas_x": 420.0,
  "canvas_y": 180.0
}
```

Одна операция описывает все три состояния задачи, потому что для
пользователя это одно и то же перетаскивание карточки:

| `wbs_node_id` | координаты | результат                        |
| ------------- | ---------- | -------------------------------- |
| задан         | игнорируются | задача в разделе ИСР           |
| `null`        | заданы     | задача лежит на холсте           |
| `null`        | `null`     | задача в списке-пуле             |

Endpoints `assign` и `assignment` остаются как частные случаи этой операции.

---

Предложение структуры моделью (см. §56):

```http
POST /projects/{project_id}/wbs/suggestion
POST /projects/{project_id}/wbs/suggestion/apply
```

---

# 11. Удаление WbsNode

Удаление структурного узла требует явного поведения.

При удалении узла, содержащего задачи, нельзя удалять сами Task.

Минимальный вариант:

```text
Удалить раздел
↓
все непосредственно привязанные задачи
получают wbs_node_id = NULL
```

Если узел имеет дочерние структурные элементы, backend не должен молча удалять дерево.

Frontend должен предложить понятное действие.

Например:

```text
Раздел содержит:

3 подраздела
8 задач

[Отмена]

[Удалить раздел и вернуть задачи в пул]
```

После подтверждения дочерние WbsNode могут быть удалены каскадно в рамках транзакции, а Task становятся нераспределёнными.

---

# 12. Получение структуры

Frontend должен получать структуру таким образом, чтобы её можно было собрать без N+1 API-запросов.

Желательно одним endpoint получить:

- WbsNode проекта;
- минимальное представление назначенных Task;
- агрегаты по узлам.

Например:

```json
{
  "nodes": [...],
  "tasks": [...],
  "stats": {...}
}
```

или дерево в соответствии с текущими API-паттернами проекта.

Не делать запрос отдельно для каждого WbsNode.

# 14. Task Pool

Левая панель содержит задачи проекта, которые ещё не распределены по структуре.

Заголовок:

```text
Unassigned Tasks     18
```

Панель должна иметь возможность:

- поиска;
- фильтрации;
- сортировки;
- drag & drop.

Минимальные фильтры:

- status;
- priority;
- deadline;
- при необходимости assignee.

По умолчанию отображать только:

```text
wbs_node_id = NULL
```

Дополнительно можно предусмотреть переключатель:

```text
Unassigned
All Tasks
```

`All Tasks` полезен для поиска уже размещённой задачи и переноса её в другой раздел.

---

# 15. Представление задачи в Task Pool

Task Pool не должен использовать огромную Kanban Card.

Нужна компактная draggable-карточка:

```text
TASK-142                   HIGH

Реализовать API фильтрации

● In Progress        08 Sep
```

Допустимо отображать:

- ID;
- название;
- status;
- priority;
- deadline.

Описание и комментарии здесь не нужны: они увеличат высоту списка.

По клику на задачу должен открываться существующий Task Detail Drawer.

---

# 16. Canvas

Основная правая область реализуется на базе:

```text
@xyflow/react / React Flow
```

Canvas должен поддерживать:

- pan;
- zoom;
- zoom controls;
- `Fit View`;
- minimap;
- background grid/dots;
- выбор узла;
- drag & drop задач из sidebar;
- визуальное выделение узлов;
- автоматическую раскладку.

Canvas визуально должен напоминать рабочую область Figma/Miro, но **не предоставлять свободное рисование**.

# 17. Позиционирование: структура и холст

Координаты **структуры** не являются частью бизнес-модели.

Backend не хранит `x`/`y` для WbsNode и для задач, размещённых в разделах.
Положение рассчитывается frontend auto-layout engine на основании:

```text
parent_id
position
wbs_position
```

Пользователь не выравнивает блок-схему руками: он задаёт структуру, а
геометрию считает раскладка.

## Исключение: карточки вне структуры

Задача, ещё не связанная с разделом, может просто лежать на холсте. Для
таких карточек координаты хранятся (`canvas_x`, `canvas_y`), потому что
иначе разложенный «стол» разъедется после перезагрузки и не будет виден
второму участнику проекта.

```text
задача в структуре      → координаты считает layout
задача вне структуры    → координаты задал пользователь
```

Как только задача получает раздел, координаты очищаются: она уходит в
блок-схему и подчиняется раскладке.

Это компромисс осознанный: он даёт привычный сценарий «накидать карточки,
потом связать», не превращая саму ИСР в свободный холст, который расползается.

---

# 18. Auto Layout

Рекомендуется использовать:

```text
ELK / elkjs
```

для вычисления layout.

Допустим другой layout engine, если он лучше интегрируется с существующим кодом, но необходимо сохранить принцип автоматического расположения.

Минимально поддержать два режима:

```text
Vertical    (по умолчанию)
Horizontal
```

ИСР почти всегда рисуют сверху вниз, поэтому вертикальный режим — режим
по умолчанию.

Раскладку получают только разделы. Задачи встают **стопкой под своим
разделом** — так ветка читается как блок-схема и не расползается вширь при
десятке задач. Раздел резервирует место под собственную стопку, чтобы
соседние ветки на неё не наехали.

### Vertical

```text
        ┌─────────┐
        │ PROJECT │
        └────┬────┘
      ┌──────┴──────┐
┌─────┴────┐  ┌─────┴────┐
│ 1 Аналит.│  │ 2 Backend│
└─┬────────┘  └─┬────────┘
  ├─ TASK-11    ├─ TASK-30
  └─ TASK-12    └─ TASK-31
```

### Horizontal

```text
┌─────────┐   ┌───────────┐
│ PROJECT ├──►│ 1 Аналитика│
└─────────┘   └─┬─────────┘
                ├─ TASK-11
                └─ TASK-12
```

Переключение layout меняет только визуализацию.

Структура данных не меняется.

---

# 19. Project Root

Корнем graph всегда является Project.

Project node не является WbsNode.

Он отображается системой автоматически.

Например:

```text
┌───────────────────────────────┐
│ PROJECT                       │
│                               │
│ Assistant Vera                │
│                               │
│ 38 tasks              64%     │
└───────────────────────────────┘
```

Пользователь не может:

- удалить root;
- переместить root;
- сделать другой узел root.

---

# 20. Structural Node

WbsNode должен иметь собственный custom React Flow node.

Пример:

```text
┌────────────────────────────┐
│ 01                         │
│ BACKEND                    │
│                            │
│ 8 tasks             63%    │
│ ████████████░░░░░          │
└────────────────────────────┘
```

Необходимо показывать:

- вычисленный WBS-number;
- title;
- количество задач;
- агрегированный progress;
- при наличии — количество проблемных/просроченных задач.

Не перегружать узел.

---

# 21. Вложенные уровни

Разные уровни могут немного отличаться визуально.

### Level 1

Самые выраженные structural nodes.

```text
01 Backend
02 Frontend
03 Deployment
```

### Level 2+

Более компактные.

```text
01.01 API
01.02 Database
```

При этом не создавать отдельный радикально отличный дизайн на каждом уровне.

Иерархия должна считываться:

- расположением;
- связями;
- WBS-number;
- небольшими изменениями размера/типографики.

---

# 22. Task Node

Task внутри ИСР не должна выглядеть как полноценная Kanban Card.

Использовать компактный custom node:

```text
┌──────────────────────────────────┐
│ TASK-142                  HIGH   │
│ Реализовать API фильтрации       │
│ ● In Progress          08 Sep    │
└──────────────────────────────────┘
```

Это позволяет видеть большое количество задач одновременно.

Task Node должен показывать:

- ID;
- title;
- status;
- priority;
- deadline.

По клику:

```text
open existing Task Detail Drawer
```

Не создавать отдельный редактор Task специально для WBS.

---

# 23. Edges

Связь всегда отражает данные, а не рисуется сама по себе:

```text
WbsNode.parent_id     связь разделов
Task.wbs_node_id      привязка задачи
```

## Связи разделов

Формируются автоматически. Пользователь не тянет связь между разделами:
иерархия меняется перетаскиванием самого раздела (§29, §30).

## Привязка задачи

Стрелку «раздел → задача» пользователь может провести сам, от нижней точки
раздела к карточке. Проведённая стрелка **и есть** привязка:

```text
провести стрелку   → Task.wbs_node_id = раздел
удалить стрелку    → Task.wbs_node_id = NULL, карточка остаётся на холсте
```

Рекомендуемый стиль:


Default edge:

```css

stroke-width: 1.2;
```

При selection/hover:

# 25. Drag Task из Task Pool

- его border становится accent;
- background слегка подсвечивается;

# 26. Цели сброса задачи

Валидные цели:

| Цель            | Результат                                              |
| --------------- | ------------------------------------------------------ |
| WbsNode         | задача уходит в конец списка раздела                    |
| другая Task     | задача встаёт рядом с ней в том же разделе (см. §28)    |
| пустой canvas   | задача просто лежит на холсте, вне структуры (см. §17)  |
| Task Pool       | задача возвращается в список нераспределённых           |

Нельзя бросать задачу на edge и на предложенный моделью раздел (§56): пока
черновик не применён, его разделов в проекте нет.

Верхняя и нижняя половина карточки-соседа задают, встать до неё или после.

Сброс на пустое место — это отдельный, намеренно разрешённый сценарий:
сначала разложить карточки как на столе, связать их позже.

# 28. Перенос Task между разделами и порядок внутри раздела

Task Node можно взять и перенести:

```text
Backend / API
↓
Backend / Database
```

Backend получает новое:

```text
wbs_node_id
```

Внутри раздела задачи упорядочены, и порядок задаёт пользователь: карточка,
брошенная на верхнюю половину соседа, встаёт перед ним, на нижнюю — после.

Клиент передаёт только соседа:

```json
{ "wbs_node_id": 32, "before_task_id": 88 }
```

Позицию (`wbs_position`) и уплотнение разреженных значений считает backend —
ровно так же, как для разделов (§6).

Статус и остальные свойства Task остаются прежними.

# 51. Не делать

Запрещённые или нежелательные подходы:

### Свободный canvas для структуры

Не разрешать пользователю вручную расставлять WbsNode как в Figma. Свободно
двигаются только карточки вне структуры (§17).

### Ручные связи разделов

Пользователь не рисует иерархию разделов мышью. Единственная связь, которую
он проводит сам, — привязка задачи к разделу (§23).

### Хранение x/y как структуры

Координаты структуры не являются бизнес-данными. `canvas_x`/`canvas_y`
хранятся только для задач вне структуры и очищаются при привязке.

### Отдельные WBS Task

Не копировать Task в отдельную сущность.

### Структурные задачи-заглушки

Не создавать фиктивную Task `Backend` только ради parent/child.

Использовать WbsNode.

### Дублирование status

WBS не имеет собственного статуса Task.

### Избыточная анимация

Не превращать рабочий инструмент в демонстрацию эффектов.

# 56. Предложение ИСР моделью

Кнопка `Предложить ИСР` просит модель разложить **существующие** задачи
проекта по разделам «по правилам индустрии»: разделы описывают результаты и
этапы, каждая задача попадает ровно в один раздел, глубина — до трёх уровней.

## Черновик, а не изменение

Запрос ничего не меняет в проекте. Ответ модели — черновик:

```text
nodes        предложенные разделы с временными temp_id
assignments  task_id → temp_id раздела
summary      объяснение логики разбиения
skipped      задачи, которым модель не нашла места
```

Черновик рисуется на том же холсте пунктиром: предложенные разделы получают
отрицательные идентификаторы и проходят через ту же раскладку, что и
сохранённые. Перетаскивать их и редактировать структуру внутри черновика
нельзя — он либо применяется, либо отменяется.

## Правка черновика

В панели справа пользователь может:

- переименовать предложенный раздел;
- удалить раздел вместе с его подразделами;
- исключить отдельную задачу из предложения.

Исключённые задачи остаются там, где были.

## Применение

`POST .../wbs/suggestion/apply` принимает **отредактированный** черновик и
проверяет его целиком заново: backend не доверяет тому, что когда-то ответила
модель. Проверяются уникальность temp_id, существование родителей, отсутствие
циклов, глубина, принадлежность задач проекту и отсутствие повторов.

Разделы создаются и задачи переносятся одной транзакцией: частично
применённое предложение хуже, чем неприменённое.

Существующие разделы не удаляются — предложение добавляется к структуре, а
лишнее пользователь убирает сам.

## Границы

- Модель не придумывает задачи и не меняет их содержание.
- В контекст уходит не больше 300 задач проекта.
- Ответ модели — недоверенные данные: ссылки на чужие задачи, повторные
  размещения и разделы глубже допустимого отбрасываются молча.
