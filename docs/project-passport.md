# Паспорт проекта и настройка канбана

Реализовано 7 сентября 2026 года. Проект остаётся простым трекером для небольшой команды: единственная настраиваемая схема работы — стадии канбана. Паспорт — структурированное описание того же проекта, без отдельной сущности и дополнительных режимов конфигурации.

## Создание и редактирование

- Название и код проекта. Код используется в номерах задач и в интерфейсе после создания не меняется.
- Описание: **проблема**, **цель**, **ожидаемый результат**, **дополнительно**. Блоки необязательны; подсказки помогают сформулировать содержание.
- Руководитель — автор создания (`owner_id`), подставляется автоматически и показан в паспорте. Передача руководства в этот сценарий не входит.
- Команда задаётся сразу или позже. При создании вводятся точные логины существующих активных пользователей через запятую; используется существующий механизм приглашения по известному логину. Руководитель входит автоматически, повторы убираются. Неизвестный участник отклоняет весь запрос до сохранения проекта. Позже состав меняется в настройках или разделе «Команда» по прежним правилам прав: управляет руководитель.
- Начало проекта при создании заполнено сегодняшней датой, его можно изменить. Окончание необязательно. Окончание не может быть раньше начала; сервер проверяет также частичное изменение периода.

В «Пульсе» показаны описание, руководитель, команда и период. В настройках собраны паспорт, история срока, управление командой и стадии.

## Правило изменения окончания

| Действие | Нужна причина |
|---|---|
| Первое назначение при создании | Нет |
| Первое назначение позже, если срок никогда не задавался | Нет |
| Сохранение той же даты | Нет, новая запись истории не создаётся |
| Перенос ранее назначенной даты вперёд или назад | Да |
| Удаление ранее назначенной даты | Да |
| Назначение после удаления даты | Да |

Причина не может состоять из пробелов. История хранит прежнюю и новую дату, идентификатор и снимок имени автора, время и комментарий. Первое назначение тоже записывается. Редактирования или удаления отдельных записей через API нет; удаление проекта удаляет его историю.

Правило проверяется в сервисе для всех PATCH-запросов. Флаг `due_date_has_been_set` сохраняется после удаления срока. Изменение проекта, запись истории и задание индексации фиксируются общей транзакцией.

Форма передаёт `expected_due_date` при изменении срока. Несовпадение с актуальным значением возвращает 409; форма показывает актуальный прежний срок и просит заново указать причину. Неизменённый срок исключается из PATCH. Сервер блокирует строку проекта на время изменения, поэтому история записывает фактическую последовательность изменений. Старые API-клиенты могут не передавать `expected_due_date`, но обязательную причину должны передавать.

## Канбан проекта

При создании форма получает стандартные стадии через `GET /api/v1/projects/defaults`. Пользователь может менять названия, цвета, порядок и признак завершающей стадии, добавлять и удалять колонки. Начальный набор — от 1 до 30 стадий с различающимися непустыми названиями. Незаданный набор в API означает серверные стадии по умолчанию.

Проект, участники и начальные стадии создаются одной транзакцией. После создания работают существующие операции со стадиями: добавление, переименование, цвет, признак завершения, перестановка и удаление пустых колонок. Последнюю стадию или стадию с задачами удалить нельзя. Перестановка перенумеровывает все затронутые колонки внутри проекта, сохраняя идентификаторы стадий и связи задач. Стандартный набор и другие проекты не меняются.

## Совместимость описания и поиск

`projects.description_sections` хранит четыре блока; сервер собирает их в `description_md` с Markdown-заголовками. Поэтому новые тексты попадают в существующие FTS, проектный документ Qdrant и сценарии AI через прежнее общее описание. При изменении блоков ставится существующее задание обновления проектного документа.

Старые описания миграция не меняет. Форма показывает их целиком в «Дополнительно», чтобы пользователь мог разнести текст по блокам постепенно. Старый API с `description_md` поддержан: явная запись свободного текста сбрасывает структурированную версию, исключая два расходящихся описания.

История сроков пока отдельным источником AI-вики не является. Полное покрытие сущностей знаниями остаётся отдельной комплексной задачей из [аудита](PROJECT_KNOWLEDGE_COVERAGE_AUDIT.md).

## Миграция и проверка

Миграция `e2f47a910c63` добавляет блоки описания, флаг ранее назначенного срока и таблицу `project_deadline_changes`. Для существующих ненулевых сроков выставляется флаг и записывается системная начальная запись «Срок на момент включения истории изменений». Прошлые переносы и даты, удалённые до этой миграции, восстановить из текущей строки проекта нельзя.

Перед запуском обновлённого backend нужно применить миграции обычным способом проекта; для локального запуска из `backend`:

```powershell
.\venv\Scripts\alembic.exe upgrade head
```

Добавлены проверки доменных правил срока, частичного обновления периода, API-автора, допустимых стадий, реальных транзакций и FTS в PostgreSQL, сохранения данных при upgrade/downgrade, изоляции порядка стадий между проектами и браузерных сценариев создания/изменения паспорта.
