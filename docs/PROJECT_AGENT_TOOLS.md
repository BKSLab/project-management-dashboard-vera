# Инструменты проектного агента

Реестр: [`backend/src/agent/action_catalog.py`](../backend/src/agent/action_catalog.py).
Схемы: [`backend/src/schemas/project_tool_inputs.py`](../backend/src/schemas/project_tool_inputs.py).
Общий исполнитель: [`AgentActionsService`](../backend/src/services/agent_actions.py).

На 21.09.2026: **60 проектных операций**, из них 43 изменяющие и 14 с отдельным подтверждением. Внутренний чат также получает четыре инструмента знаний и `get_tool_schemas`: всего **65**. Проект и инициатор всегда приходят от аутентифицированного транспорта, а не из аргументов модели.

## Покрытие

| Область | Инструменты | Возможности |
|---|---|---|
| Знания | `search_sources`, `list_sources`, `read_source`, `related_sources` | Поиск, страницы полных источников, переход по связям |
| Схемы | `get_tool_schemas` | Точные схемы до восьми выбранных инструментов |
| Проект | `get_project`, `update_project` | Паспорт, статистика, настройки, ключ и история сроков; изменение владельцем |
| Задачи | `list_tasks`, `get_task`, `create_task`, `update_task`, `move_task`, `delete_task` | Поиск, CRUD, канбан, сроки, приоритет, роли, исполнитель, постановщик и наблюдатели |
| Чек-листы | `set_checklist` | Создание, полная правка, порядок, отметки пунктов и удаление с проверкой версии |
| Базовый план | `fix_task_baseline` | Фиксация текущих дат задачи после решения участника |
| Комментарии | `list_comments`, `add_comment`, `update_comment`, `delete_comment` | Обсуждение, серверное авторство, правка прочитанной версии и удаление |
| Команда | `list_members`, `add_member`, `remove_member`, `transfer_project_ownership` | Добавление зарегистрированного пользователя, удаление назначений и передача владения |
| Стикеры | `list_stickers`, `create_sticker`, `update_sticker`, `move_sticker`, `delete_sticker` | Текст, палитра, задачи, координаты, размеры и ревизии |
| Документы | `list_documents`, `get_document`, `create_document`, `update_document`, `delete_document`, `link_document`, `unlink_document` | Markdown-документы и связи с задачами текущего проекта |
| Файлы | `list_attachments`, `attach_uploaded_file`, `copy_attachment`, `create_text_attachment`, `delete_attachment` | Метаданные, копия пользовательской загрузки в задачу, копирование между задачами и создание текстового файла |
| Стадии | `list_stages`, `create_stage`, `update_stage`, `delete_stage` | Имя, цвет, порядок и признак завершения с обычными ограничениями канбана |
| ИСР | `get_structure`, `create_wbs_node`, `update_wbs_node`, `move_wbs_node`, `delete_wbs_node`, `place_task` | Разделы, иерархия, порядок, распределение задач и возврат в пул |
| Вехи | `list_milestones`, `create_milestone`, `update_milestone`, `delete_milestone` | Даты, состояние и привязка вех к ИСР |
| Зависимости | `list_dependencies`, `create_dependency`, `delete_dependency` | Связи задач, лаг, проверка проекта обеих задач и циклов |
| Календарь | `get_calendar`, `preview_schedule_change`, `apply_schedule_change` | Чтение диапазона, расчёт последствий и подтверждённое применение версий дат |
| Риски | `list_risks`, `get_risk`, `create_risk`, `update_risk`, `delete_risk` | Фильтры, оценки, владелец, планы, связанная задача, статусы вплоть до CLOSED |

Используются существующие роли доступа `OWNER` и `MEMBER`. Передача владения меняет обе роли и владельца проекта одной транзакцией. Добавление участника требует уже зарегистрированного логина; регистрация пользователей, портфельные операции и удаление всего проекта не входят в область проектного агента.

Списки с `offset`/`limit` возвращают `next_offset`; реестр рисков использует `page`/`page_size` и фильтры доменного сервиса. Структура ИСР, стадии, календарь и файлы задачи сохраняют существующие агрегатные контракты; число файлов задачи ограничено 20. Для больших текстов доступны страницы `read_source`. Текстовые файлы, создаваемые моделью: `.txt`, `.md`, `.csv`, `.log`; пользовательские загрузки допускают все форматы вложений задач.

## Пример рабочего цикла

1. «Есть ли задача на тестирование окна заказа?» — `list_tasks` и при необходимости `search_sources`; запись недоступна без поручения.
2. «Создай её и назначь Ивану» — `list_members`, точная схема `create_task`, затем создание с проверенным ID исполнителя.
3. «Добавь критерии и прикрепи файл» — `get_task`, `set_checklist` с текущей ревизией, `attach_uploaded_file` с ID пользовательской загрузки.
4. «Удали эту задачу» — `get_task`, `delete_task` с `expected_updated_at`; агент возвращает карточку ожидания.
5. Участник нажимает «Подтвердить» — сервер выполняет сохранённую операцию, журнал и данные фиксируются вместе, агент объясняет результат.

При конфликте версии нужна новая проверка объекта. Новая формулировка не должна использоваться для обхода отклонённой карточки. Завершённые действия передаются в контекст повторной попытки; частично выполненный запрос должен сообщать уже завершённые операции отдельно от оставшихся.

## MCP

MCP остаётся внутри FastAPI на `/mcp`. Новых сервисов в Docker Compose нет. Прежние именованные инструменты сохранены для совместимости. Для полного каталога используются:

- `list_project_tools(project_key, names?)`: краткий список; `names` раскрывает схемы до восьми операций. READ-токен видит только операции чтения.
- `execute_project_tool(project_key, name, arguments, request_id?)`: та же операция и тот же `AgentActionsService`, что в чате. Для записи обязателен стабильный UUID `request_id`; при потере ответа повторяется тот же UUID с теми же аргументами.

Числовые ID во вложенных `arguments` берутся из результатов общих инструментов. `project_key` задаёт область; проверка сервиса запрещает ресурсы другого проекта, даже если владелец токена участвует в нём.

Операции с подтверждением сначала сохраняются как `pending`, затем адаптер вызывает **MCP form elicitation** с конкретным проектом, объектом и параметрами. Клиент должен показать форму участнику. Решение не является аргументом инструмента, и отдельного инструмента самоподтверждения нет. После ответа повторно проверяется токен. Если клиент не поддерживает elicitation, действие остаётся невыполненным; его можно продолжить тем же `request_id` в поддерживающем клиенте. `cancel` сохраняет ожидание, `reject` закрывает его без изменений.
