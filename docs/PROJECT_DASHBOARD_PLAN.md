# Дашборд управления проектом — актуальная архитектура

> Статус на 2026-08-02: основной таск-трекер, ИСР, документы, поиск, логирование и инфраструктура реализованы. Документ описывает текущее состояние, а не первоначальный MVP-план.

## 1. Назначение

Project Management Dashboard Vera — внутренний рабочий инструмент для ведения конкретного проекта. Базовая ИСР загружается один раз из снэпшота, после чего PostgreSQL становится рабочим источником данных для канбана, сроков, комментариев, документов и истории изменений.

Основные пользовательские сценарии:

1. видеть состояние проекта на главной странице;
2. вести задачи на канбан-доске;
3. открывать задачу в центральном модальном окне и работать со всеми её деталями;
4. контролировать прогресс фаз через дерево ИСР;
5. хранить и связывать проектные документы;
6. искать информацию по задачам, комментариям, документам и кодам ИСР.

Авторизация не входит в текущий контур и не должна добавляться без отдельного решения.

## 3. Backend-архитектура

Обязательное направление зависимостей:

```text
Endpoint → Service → Repository → Database
```

### Endpoint

- принимает и документирует HTTP-параметры;
- пишет лог начала и завершения запроса;
- получает только готовый сервис через Depends;
- локально преобразует доменные исключения в `HTTPException`;
- не импортирует сессию или репозиторий.

### Service

- реализует пользовательский сценарий;
- объединяет данные нескольких репозиториев;
- отвечает за правила ИСР ↔ канбан;
- не использует FastAPI и не формирует SQL;
- преобразует repository errors в service errors.

### Repository

- работает только со своей таблицей/моделью;
- выполняет SQLAlchemy-запросы;
- делает commit для записи и rollback при ошибке;
- отдельно обрабатывает `IntegrityError` известных ограничений;
- не собирает агрегаты соседних доменов.

### Dependency Injection

```text
dependencies/db_session.py
    ↓
dependencies/repositories.py
    ↓
dependencies/services.py
    ↓
api/v1/endpoints/*.py
```

Правила и примеры подробно зафиксированы в корневом `FASTAPI_PATTERNS.md`.

## 4. Доменные сущности

### Document

Markdown-документ с уникальным `slug`, заголовком, содержимым и вычисляемым FTS-вектором.

### WbsItem

Узел дерева ИСР:

- `parent_id` задаёт иерархию;
- `code` уникален;
- `phase_name` используется у корневых фаз;
- `role` хранит ответственную роль;
- `order_index` определяет порядок среди соседей;
- `is_leaf` показывает, должна ли существовать связанная карточка канбана.

### KanbanStage

Колонка доски с названием, цветом, порядком и признаком завершающей стадии.

### KanbanTask

Карточка канбана. Ручная задача имеет `wbs_item_id = NULL`; листовая работа ИСР связана ровно с одной задачей. `position` отвечает за пользовательский порядок карточек внутри стадии.

### TaskComment

Комментарий задачи с опциональным именем автора. Текст и автор входят в FTS-вектор.

### TaskActivity

Неизменяемая история значимых событий:

- смена стадии;
- смена срока;
- изменение описания;
- добавление комментария.

### DocumentLink

Связь документа ровно с одной целью: задачей канбана или узлом ИСР. Это правило защищено и Pydantic/service-валидацией, и CHECK constraint PostgreSQL. Повторные связи запрещены уникальными ограничениями.

### SeedState

Версионированный маркер успешной загрузки базовой ИСР. Маркер не заменяет проверку данных: при старте ожидаемые узлы, стадии и листовые задачи проверяются повторно.

## 5. ИСР и канбан

Для листовых узлов ИСР действует связь 1:1 с задачами:

- при создании листа создаётся задача в «Бэклоге»;
- при добавлении дочернего узла бывший лист становится разделом, а его карточка удаляется;
- изменение названия листа синхронизирует заголовок задачи;
- удаление ветки рекурсивно удаляет связанные карточки;
- перемещение карточки меняет стадию и записывает событие истории;
- прогресс раздела вычисляется по количеству листьев в завершающей стадии.

Сортировка задач сохраняет предметный порядок. FTS-поиск фильтрует набор, но не заменяет его сортировкой по rank.

## 6. Полнотекстовый поиск

Поиск реализован для:

| Таблица | Вектор | Вес A | Вес B |
|---|---|---|---|
| `documents` | `search_vector` | `title` | `content_md` |
| `kanban_tasks` | `search_vector` | `title` | `description_md` |
| `task_comments` | `search_vector` | `body_md` | `author_name` |

Векторы являются `GENERATED ALWAYS AS ... STORED`, для каждого создан GIN-индекс. Запрос использует `websearch_to_tsquery`; простой пользовательский текст дополняется безопасным prefix query. Минимальная длина префикса — три символа.

Подсветка строится через `ts_headline` и безопасные текстовые маркеры. HTML из PostgreSQL не принимается: frontend сам рендерит выделение через компонент `SearchHighlight`.

По коду ИСР и slug применяется экранированный `ILIKE`, поскольку эти поля не являются естественным русским текстом.

## 7. API v1

Базовый префикс: `/api/v1`.

### Документы

| Метод | Маршрут |
|---|---|
| GET, POST | `/documents` |
| GET, PATCH, DELETE | `/documents/{slug}` |
| GET | `/documents/{slug}/links` |

### Канбан

| Метод | Маршрут |
|---|---|
| GET, POST | `/kanban/stages` |
| PATCH, DELETE | `/kanban/stages/{stage_id}` |
| GET, POST | `/kanban/tasks` |
| GET, PATCH, DELETE | `/kanban/tasks/{task_id}` |
| PATCH | `/kanban/tasks/{task_id}/move` |
| GET, POST | `/kanban/tasks/{task_id}/comments` |
| DELETE | `/kanban/comments/{comment_id}` |
| GET | `/kanban/tasks/{task_id}/activity` |
| GET | `/kanban/tasks/{task_id}/links` |

### ИСР и связи

| Метод | Маршрут |
|---|---|
| GET | `/wbs/tree` |
| POST | `/wbs/items` |
| PATCH, DELETE | `/wbs/items/{item_id}` |
| POST | `/document-links` |
| DELETE | `/document-links/{link_id}` |

Все endpoint-ы содержат summary, description, operation ID, response description и примеры ошибок. Системная ошибка валидации обрабатывается глобально; доменные ошибки — локально в endpoint-е.

## 8. Frontend

### Главная

- сводные числа по ИСР, задачам и документам;
- шкалы «Пульса канбана» по стадиям;
- ближайшие сроки и быстрые переходы.

### Канбан

- колонки отсортированы по `order_index`;
- карточки перемещаются через optimistic update;
- поиск работает по задачам, комментариям и коду ИСР;
- совпадение явно подсвечивается;
- клик открывает `TaskModal`, а не правый sidebar;
- модальное окно содержит описание, срок, документы, комментарии и историю;
- scrollbar модального окна использует общий стиль интерфейса.

### ИСР

- дерево фаз/разделов/работ;
- раскрытие веток;
- rollup-прогресс;
- CRUD узлов;
- переход к связанной карточке канбана.

### Документы

- полнотекстовый поиск;
- список с фрагментами совпадений;
- создание, Markdown-редактирование и удаление;
- просмотр связанных задач и узлов ИСР.

## 9. Логирование

Логирование настраивается через `backend/logging.ini`.

- каждый модуль использует `logging.getLogger(__name__)`;
- endpoint пишет `🚀` на входе и `✅` после успеха;
- финальная обработка доменной ошибки пишет traceback через `logger.exception`;
- сервисы и репозитории логируют внутренний контекст через `logger.error(..., exc_info=True)`;
- lifespan проверяет БД и базовые данные до готовности приложения;
- Docker entrypoint включает access/error logs Hypercorn в stdout.

Если backend стартовал, но запросов endpoint-ов в его консоли нет, первым делом нужно проверить, не занимает ли порт `8000` старый процесс.

## 10. Начальные данные

`backend/scripts/data/wbs_seed.json` содержит базовую ИСР. Загрузчик:

1. валидирует JSON и порядок родителей;
2. проверяет/создаёт пять базовых стадий;
3. добавляет отсутствующие узлы по уникальному коду;
4. добавляет отсутствующие задачи листьев;
5. повторно проверяет ожидаемые коды и связи;
6. сохраняет маркер `vera_wbs_v1`.

Наличие маркера без фактических данных не считается успешным состоянием. Существующие пользовательские значения не перезаписываются. Удалённая базовая запись будет восстановлена, пользовательские дополнительные записи сохраняются.

Миграции Alembic не выполняют импорт или очистку данных.

## 11. Миграции и ограничения

Актуальная цепочка включает:

- исходную схему;
- FTS-векторы и GIN-индексы;
- серверные defaults timestamps;
- таблицу `seed_state`;
- комментарии колонок;
- CHECK/UNIQUE constraints связей документов;
- уникальный код ИСР;
- именованное ограничение связи задачи с ИСР.

`alembic check` должен возвращать `No new upgrade operations detected`.

## 12. Тестирование

Тестовая пирамида:

- unit-тесты сервисов с `AsyncMock(spec=Repository)`;
- API-тесты через `dependency_overrides` и ASGI transport;
- integration-тесты репозиториев на настоящем PostgreSQL через Testcontainers.

Локальные команды:

```bash
cd backend
ruff check .
ruff format --check .
flake8 .
pytest -q
alembic check

cd ../frontend
npm run lint
npm run build
```

Автоматический CI пока не используется. Проверки выполняются локально перед отправкой изменений.

## 13. Docker-схема

```text
browser → nginx:93
             ├── /      → frontend
             └── /api/  → backend:8000
                              └── PostgreSQL:5432
```

Backend-контейнер использует одного Hypercorn worker. Перед сервером `entrypoint.sh` применяет миграции и выполняет проверяемую загрузку ИСР. Документы автоматически не импортируются.

## 14. Следующие возможные улучшения

- авторизация — только отдельной задачей и после выбора модели доступа;
- пагинация обычных растущих списков без нарушения полного состояния канбана/ИСР;
- `pg_trgm` как fallback для опечаток;
- Hunspell при подтверждённой необходимости более точной морфологии;
- code splitting крупного frontend bundle;
- автоматический CI, когда появится потребность в удалённом pipeline.
