# Task Tracker — актуальная архитектура

> Статус на 2026-09-01: проект стал корневой сущностью, backend и интерфейс переписаны. Остаётся интерактивный конструктор ИСР по [`WBS_BUILDER_SPEC.md`](WBS_BUILDER_SPEC.md).

## 1. Назначение

Внутренний рабочий инструмент для ведения нескольких проектов. Всё в трекере отталкивается от проекта: задачи, стадии канбана, документы и статистика существуют только внутри него.

Основные пользовательские сценарии:

1. видеть состояние всех проектов на общем дашборде;
2. вести задачи проекта на канбане и в списке;
3. открывать задачу в правой панели, не теряя контекст экрана;
4. организовывать задачи в структуру работ и следить за прогрессом разделов;
5. хранить и связывать проектные документы;
6. искать по задачам, комментариям, номерам и документам внутри проекта.

Авторизация не входит в текущий контур и не должна добавляться без отдельного решения.

## 2. Технологический стек

### Backend

Python 3.12, FastAPI, Hypercorn, PostgreSQL 16, SQLAlchemy 2 async + asyncpg, Alembic, Pydantic v2 и pydantic-settings, pytest, Ruff, Flake8, Testcontainers.

### Frontend

React 19, TypeScript, Vite, Tailwind CSS v4, TanStack Query, Zustand, `@dnd-kit`, `react-aria-components`, `lucide-react`, Markdown-конвейер с DOMPurify.

### Инфраструктура

Docker Compose: PostgreSQL, backend, frontend и nginx как единая точка входа на порту `93`.

## 3. Backend-архитектура

Обязательное направление зависимостей:

```text
Endpoint → Service → Repository → Database
```

### Endpoint

Принимает и документирует HTTP-параметры, пишет лог начала и завершения запроса, получает готовый сервис через `Depends`, локально преобразует доменные исключения в `HTTPException`. Не импортирует сессию или репозиторий.

### Service

Реализует пользовательский сценарий, объединяет данные нескольких репозиториев, отвечает за инварианты домена, преобразует repository errors в service errors. Не использует FastAPI и не формирует SQL.

### Repository

Работает только со своей таблицей, выполняет SQLAlchemy-запросы, делает commit для записи и rollback при ошибке, отдельно обрабатывает `IntegrityError` известных ограничений. Не собирает агрегаты соседних доменов.

### Dependency Injection

```text
dependencies/db_session.py → dependencies/repositories.py → dependencies/services.py → api/v1/endpoints/*.py
```

Правила и примеры зафиксированы в корневом `FASTAPI_PATTERNS.md`.

## 4. Доменные сущности

### Project

Корневая сущность: `key` (короткий код, префикс номеров задач), `name`, `description_md`, `status`, `color`, `icon`, `start_date`, `due_date`, `order_index`, FTS-вектор. Удаление проекта каскадно удаляет его стадии, задачи, структуру и документы, а сервис дополнительно чистит каталоги вложений.

### ProjectStage

Колонка канбана конкретного проекта: `name`, `order_index`, `color`, `is_done_stage`. Название уникально внутри проекта. При создании проекта копируется шаблон из пяти стадий.

### Task

Задача проекта. `number` уникален внутри проекта и отображается как `KEY-142`. `stage_id` отвечает за состояние работы, `wbs_node_id` — за место в структуре; признаки независимы. Есть `priority`, `role` и свободное поле `assignee`.

### WbsNode

Структурный контейнер ИСР: `project_id`, `parent_id`, `title`, `position`. Не задача: нет статуса, срока и приоритета. Номера и координаты не хранятся — они выводятся из `parent_id` и `position`.

### Document и DocumentLink

Markdown-документ принадлежит проекту, `slug` уникален внутри проекта. Связь соединяет документ и задачу одного проекта.

### TaskComment, TaskActivity, TaskAttachment

Комментарии, неизменяемая история значимых изменений и метаданные файлов задачи.

## 5. Инварианты, которые проверяет сервисный слой

БД не может выразить эти правила, поэтому они живут в сервисах:

- стадия задачи принадлежит тому же проекту;
- раздел ИСР принадлежит тому же проекту, что и задача;
- раздел нельзя перенести внутрь самого себя или собственного потомка;
- удаление раздела снимает привязку задач, но никогда их не удаляет;
- документ и задача в связи принадлежат одному проекту;
- последнюю стадию проекта и непустую стадию удалять нельзя.

## 6. Позиционирование и номера

Порядок задач внутри стадии и разделов внутри уровня задаётся разреженной шкалой с шагом 1000. Backend полностью владеет расчётом: клиент передаёт целевого родителя и соседа, а не готовую позицию. Когда промежуток между соседями исчерпан, сервис уплотняет весь уровень одной транзакцией.

Номера ИСР считаются на клиенте из `parent_id` и `position`, поэтому не могут разойтись со структурой. Номер задачи, наоборот, хранится: он попадает в ссылки и обсуждения и не должен меняться при перестановке.

## 7. Статистика

`ProjectStatsSchema` собирается из стадий и задач одного проекта. `DashboardSchema` считается агрегатными запросами по всему портфелю: один запрос на счётчики, один на разбивку по стадиям, один на задачи с ближайшими сроками. Количество проектов не влияет на число обращений к БД.

## 8. Frontend

Разделение состояния:

- **server state** — TanStack Query, ключи собраны в `lib/api.ts`;
- **derived state** — номера ИСР, дерево, раскладка, прогресс: считаются из server state;
- **UI state** — Zustand: выбранная задача, сайдбар, свёрнутые ветки, режим раскладки.

Одна задача имеет одно представление во всех экранах: карточка канбана, строка списка и узел структуры используют одни токены статуса и приоритета, а открываются в одну и ту же правую панель.

Дизайн-система описана в [`DESIGN_GUIDE.md`](DESIGN_GUIDE.md): токены в `frontend/src/app.css`, компоненты в `components/ui/`, локальные HEX в компонентах не допускаются.
