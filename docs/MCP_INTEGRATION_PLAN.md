# MCP-слой трекера: план реализации

Документ описывает добавление в Project Management Dashboard Vera канала MCP (Model Context Protocol) поверх HTTP, чтобы внешние AI-агенты — прежде всего Claude Code CLI — работали с трекером напрямую: вели задачи, читали и писали комментарии, искали по проекту.

Архитектурные правила backend — [FASTAPI_PATTERNS.md](../FASTAPI_PATTERNS.md). Дизайн интерфейса — [DESIGN_GUIDE.md](DESIGN_GUIDE.md).

## 1. Цель и границы

**Цель.** Пользователь один раз выпускает токен в интерфейсе трекера, вставляет готовый блок конфигурации в свой MCP-клиент и дальше работает с трекером из агента: создаёт задачи, разбирает входящие, собирает сводки, комментирует.

**В первой версии:**

- проекты — список и чтение;
- задачи — полный CRUD и перемещение по стадиям;
- комментарии — чтение и добавление;
- поиск — лексический по задачам и семантический по базе знаний проекта;
- аутентификация по API-токену с выпуском и отзывом в интерфейсе;
- раздел «MCP» в интерфейсе с готовым конфигом и описанием прав;
- два-три примера скилов.

**Не входит:** документы, ИСР, вложения, стадии проекта, управление участниками, эндпоинт `ask` Project Agent, OAuth, многопользовательские сценарии выдачи токенов администратором.

## 2. Ключевой принцип: MCP — адаптер, а не второй API

MCP-слой не содержит собственной бизнес-логики и собственных проверок доступа. Он вызывает те же сервисы, что и HTTP-эндпоинты, и опирается на те же зависимости доступа.

```text
Claude Code CLI
      │  MCP over HTTP
      ▼
  MCP-роутер (tools)
      │
      ▼
  get_current_user ──► API-токен или session cookie
      │
      ▼
  dependencies/access.py  (членство в проекте)
      │
      ▼
  Services ──► Repositories ──► PostgreSQL / Qdrant
```

Причина жёсткая: любая параллельная реализация проверки доступа рано или поздно разъедется с основной, и разъедется молча. Сейчас весь контроль сходится в две точки — [`dependencies/auth.py`](../backend/src/dependencies/auth.py) и [`dependencies/access.py`](../backend/src/dependencies/access.py), — и это надо сохранить.

## 3. Этап 1. API-токены и Bearer-аутентификация

### 3.1. Проблема

Сейчас единственный способ аутентификации — session cookie: [`get_current_user`](../backend/src/dependencies/auth.py) читает `Cookie(alias=session_cookie_name)` и разбирает JWT через `decode_access_token`. Для MCP-клиента кука не годится.

Передавать логин и пароль в заголовках нельзя: проверка пароля намеренно медленная (bcrypt/argon — порядка 100 мс), а агент делает десятки вызовов подряд; пароль осел бы открытым текстом в конфиге MCP-клиента; отозвать его можно только сменив себе вход в веб; скоупа нет.

### 3.2. Решение: непрозрачные хранимые токены

Существующий JWT остаётся для веб-сессии. Для MCP заводятся отдельные API-токены.

Почему не JWT в заголовке: интерфейс должен показывать список выданных токенов и отзывать их, а отзыв JWT требует списка отозванных — то есть той же таблицы, только с вывернутой логикой. Хранимый непрозрачный токен проще и честнее.

**Модель `api_tokens`:**

| Поле | Назначение |
|---|---|
| `id` | первичный ключ |
| `user_id` | владелец, FK на `users` |
| `name` | человекочитаемое имя, задаёт пользователь («ноутбук», «рабочая машина») |
| `token_hash` | SHA-256 от секрета; сам секрет не хранится |
| `prefix` | первые 8 символов секрета для отображения в списке |
| `scope` | `read` или `write` |
| `created_at`, `last_used_at`, `expires_at`, `revoked_at` | жизненный цикл |

Секрет — `secrets.token_urlsafe(32)`, показывается **один раз** при выпуске. Дальше в списке видны только имя, префикс, права, даты и кнопка отзыва.

`last_used_at` обновляется не на каждый запрос, а не чаще раза в несколько минут: иначе каждый вызов инструмента становится записью в БД.

### 3.3. Точка интеграции

`get_current_user` учится принимать заголовок `Authorization: Bearer <token>` в дополнение к cookie:

1. есть заголовок — ищем токен по SHA-256, проверяем `revoked_at`, `expires_at`, `is_active` пользователя;
2. нет заголовка — прежняя логика с cookie;
3. нет ни того ни другого — 401.

Это единственное изменение, которое требуется, чтобы **все** существующие эндпоинты и все зависимости доступа заработали для MCP. Поэтому его надо сделать аккуратно и покрыть тестами плотнее остального.

### 3.4. Скоупы

Два значения, без иерархии ролей:

| Scope | Что разрешает |
|---|---|
| `read` | все GET-операции над доступными пользователю проектами |
| `write` | дополнительно создание, изменение и удаление задач и комментариев |

Проекты токен не выбирает: он видит ровно то, что видит его владелец через членство в проектах. Отдельный список проектов на токен усложнил бы модель доступа ради сценария, которого пока нет.

Проверка скоупа — отдельная зависимость `RequireWriteScope`, применяемая к изменяющим инструментам. Сессия из cookie всегда считается `write`.

### 3.5. API управления токенами

| Метод | URL | Назначение |
|---|---|---|
| `GET` | `/api/v1/users/me/tokens` | список токенов без секретов |
| `POST` | `/api/v1/users/me/tokens` | выпуск; секрет возвращается один раз |
| `DELETE` | `/api/v1/users/me/tokens/{token_id}` | отзыв |

Все три доступны только по session cookie: выпускать и отзывать токены из-под самого API-токена нельзя, иначе скомпрометированный токен продлевает себе жизнь сам.

## 4. Этап 2. MCP-сервер

### 4.1. Транспорт и размещение

Streamable HTTP, смонтирован в то же приложение FastAPI отдельным роутером на пути `/mcp`.

Обоснование: переиспользуются DI, настройки, фабрика сессий, логирование и обработка исключений; не появляется второй процесс, второй Dockerfile и второй контур деплоя. Отдельный процесс имел бы смысл при потребности масштабировать MCP независимо — её пока нет.

Nginx-шлюз должен проксировать `/mcp` на backend наравне с `/api`. Streamable HTTP держит долгие соединения, поэтому в конфигурации nginx нужно снять буферизацию ответа и поднять таймаут для этого location.

### 4.2. Набор инструментов первой версии

| Инструмент | Scope | Сервис-источник |
|---|---|---|
| `list_projects` | read | `ProjectsService` |
| `get_project` | read | `ProjectsService` |
| `list_tasks` | read | `TasksService`, фильтры по стадии, приоритету, исполнителю |
| `get_task` | read | `TasksService` |
| `create_task` | write | `TasksService` |
| `update_task` | write | `TasksService` |
| `move_task` | write | `TasksService`, смена стадии |
| `delete_task` | write | `TasksService` |
| `list_comments` | read | `TaskCommentsService` |
| `add_comment` | write | `TaskCommentsService` |
| `search_tasks` | read | лексический `tsvector`-поиск |
| `search_project_knowledge` | read | семантический поиск с источниками |

`ask` Project Agent наружу не выставляется. Claude Code сам является агентом; вызов через инструмент второго агента добавил бы латентность, вторую цену за LLM и потерю контроля над контекстом. Наружу отдаётся retrieval — `search_project_knowledge`, — а рассуждает вызывающий агент.

### 4.3. Контракт инструментов

- Идентификация проекта — по `project_key` (`VERA`), задачи — по `task_key` (`VERA-142`). Числовые `id` наружу не выставляются: агент оперирует тем же, что видит человек в интерфейсе.
- Описания инструментов и параметров — на русском, с примерами значений. Их читает модель, и от их качества напрямую зависит, правильно ли она выберет инструмент.
- Ответы — компактный JSON без служебных полей. Длинные Markdown-описания обрезаются с явным указанием на усечение.
- Списки всегда с лимитом и понятным поведением по умолчанию: агент не должен нечаянно вытянуть все задачи проекта.

### 4.4. Ошибки

Доменные исключения отображаются в текст ошибки инструмента без утечки внутренних деталей:

| Ситуация | Ответ инструмента |
|---|---|
| Нет доступа к проекту | «Проект недоступен» — без различения «нет прав» и «не существует» |
| Недостаточный scope | «Токен выдан только на чтение» |
| Валидация | текст ошибки поля |
| Сбой репозитория | общая ошибка, детали только в лог |

Различать «нет прав» и «не существует» нельзя: это позволило бы перебором выяснять существование чужих проектов.

## 5. Этап 3. Раздел «MCP» в интерфейсе

Новый маршрут `/mcp` в [`App.tsx`](../frontend/src/App.tsx) и пункт в основной навигации.

Содержимое страницы, в порядке сверху вниз:

1. **Готовый блок конфигурации с кнопкой копирования.** Не абстрактная инструкция, а фрагмент, который сразу вставляется в конфиг Claude Code, с уже подставленным адресом сервера. Сразу после выпуска токена — вместе с секретом; в остальное время — с плейсхолдером на месте токена.
2. **Выпуск токена.** Имя, права (`read` / `write`), срок жизни. Секрет показывается один раз, крупно, с кнопкой копирования и явным предупреждением, что второй раз он не отобразится.
3. **Список токенов.** Имя, префикс, права, дата создания, последнее использование, кнопка отзыва с подтверждением.
4. **Что разрешает токен.** Перечень доступных инструментов и список проектов, которые видны владельцу. Это снимает вопрос «а что он вообще может» до того, как он возникнет.
5. **Примеры скилов** — раздел 6.

Оформление — существующая тёмная дизайн-система, как на остальных страницах.

## 6. Этап 4. Примеры скилов

Три сценарных примера, доступные для копирования и скачивания.

Принцип: **не по скилу на каждый метод API.** Такой набор продублировал бы список инструментов, который Claude Code и так видит, и устаревал бы при каждом изменении контракта. Ценность — в сценариях, где видна работа с трекером как с процессом.

| Скил | Что делает |
|---|---|
| «Разбор входящих» | находит задачи без стадии, приоритета или исполнителя, предлагает раскладку, применяет после подтверждения |
| «Сводка по проекту за неделю» | собирает изменения, завершённые и просроченные задачи, формирует текст для отчёта |
| «Задачи из заметки встречи» | разбирает текст заметки, предлагает список задач, создаёт их после подтверждения |

Каждый пример — готовый `SKILL.md` с описанием, вызовами инструментов и явной точкой подтверждения перед записью в трекер.

## 7. Тестирование

| Уровень | Что покрываем |
|---|---|
| Unit | выпуск и хэширование токена, отзыв, истёкший токен, скоупы, разбор заголовка `Authorization` |
| Unit | маппинг доменных исключений в ошибки инструментов |
| API | Bearer-доступ ко всем закрытым эндпоинтам; отозванный токен → 401; `read`-токен на изменяющей операции → отказ |
| API | эндпоинты управления токенами недоступны по самому API-токену |
| Integration | репозиторий токенов на настоящем PostgreSQL |
| MCP | каждый инструмент: успешный вызов, чужой проект, несуществующая сущность, недостаточный scope |
| Frontend | страница MCP: выпуск, единственный показ секрета, отзыв |

Отдельно — тест, что доступ к чужому проекту по API-токену невозможен ни одним инструментом. Это главный риск всего слоя.

## 8. Безопасность

- Секрет токена хранится только как SHA-256; в логи, в ответы API и в сообщения об ошибках не попадает никогда.
- Токен передаётся в заголовке, не в URL: URL оседают в логах прокси и в истории.
- Управление токенами закрыто для самих токенов (раздел 3.5).
- Скоуп `read` реально запрещает запись, а не только прячет инструменты: проверка на сервере, а не в описании инструмента.
- Ошибки доступа не различают «нет прав» и «не найдено».
- Ограничение частоты запросов на MCP-путь стоит рассмотреть до выставления сервера наружу; для локальной работы не требуется.

## 9. Порядок работ

| Этап | Состав | Зависимости |
|---|---|---|
| 1 | Модель, репозиторий и сервис токенов; `get_current_user` с Bearer; скоупы; API управления | нет |
| 2 | MCP-роутер, инструменты чтения (`list_*`, `get_*`, поиск) | этап 1 |
| 3 | Инструменты записи (`create/update/move/delete_task`, `add_comment`) | этап 2 |
| 4 | Раздел «MCP» в интерфейсе | этап 1 |
| 5 | Примеры скилов | этап 3 |

Этапы 2 и 4 могут идти параллельно после первого.

## 10. Открытые вопросы

1. **Адрес сервера в конфиге.** Сейчас всё работает локально через nginx на `5173`. Если трекер будет доступен извне — нужен домен и TLS, иначе токен уходит по открытому каналу. От этого зависит, что подставлять в блок конфигурации на странице MCP.
2. **Срок жизни токена по умолчанию.** Бессрочный удобнее для личного использования, ограниченный безопаснее. Предлагаю 90 дней с возможностью выбрать «без срока».
3. **Нужен ли `write` вообще в первой версии.** Если основной сценарий — чтение и сводки, то можно начать с `read`-токенов и добавить запись после реальной эксплуатации.
