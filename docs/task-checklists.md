# Чек-листы задач

У задачи может быть один чек-лист с названием и упорядоченными пунктами. Он доступен
в форме создания задачи и в общей карточке задачи из всех представлений проекта.

## Работа в интерфейсе

«Добавить чек-лист» открывает редактор. Можно изменить название, добавить,
отредактировать и удалить пункты, поменять их порядок стрелками, отметить выполнение.
При создании чек-лист сохраняется одной транзакцией с задачей. В карточке текстовые
правки сохраняются кнопкой «Сохранить чек-лист» или отменяются; отметки выполнения
сохраняются сразу. При ошибке отметка откатывается. Удаление всего чек-листа требует
подтверждения и допускает последующее создание нового.

«Сформировать чек-лист» возвращает отдельный редактируемый вариант из 3–5 пунктов.
Его можно отклонить, принять как есть или изменить перед принятием. Существующий
чек-лист заменяется только кнопкой «Заменить чек-лист». В форме новой задачи принятие
переносит предложение в черновик; сохранение происходит при создании задачи.
Все пункты нового AI-предложения изначально не отмечены.

Одновременное редактирование защищено версией: устаревшее сохранение возвращает
конфликт и оставляет ручной черновик на экране. «Загрузить актуальный чек-лист»
загружает текущее состояние и сбрасывает локальные правки и AI-предложение.
AI-предложение также связано с версией, по которой оно было сформировано.

Ручной чек-лист допускает до 100 пунктов, в том числе пустой список. Название —
до 120 символов, текст пункта — до 500; пустые названия и формулировки не сохраняются.
Завершение всех пунктов не меняет стадию задачи.

## Контекст модели

Генерация использует текущие название и описание, текущий чек-лист, выбранные
документы проекта и новые файлы. Для существующей задачи автоматически читаются
связанные документы и сохранённые вложения. Доступ к проекту и принадлежность всех
источников проверяются до чтения файлов и вызова модели.

Используется общий экстрактор текста для TXT/Markdown/CSV/LOG, DOCX, PDF, таблиц
Excel и поддерживаемых изображений через настроенное распознавание. В контексте
не более 10 файлов по 10 МиБ, сначала выбранные в форме; не более 20 документов.
Текст файла ограничен настройкой `task_rephrase_file_max_chars` и верхней границей
5000 символов. Документ передаётся фрагментом до 3000 символов, описание задачи —
до 20 000. Общий JSON ограничен 60 000 символами. Не прочитанные и сокращённые
источники перечисляются в предупреждениях пользователю и модели.

Тексты пунктов, их порядок и отметки передаются в анализ проекта и портфеля,
Project Agent, предложения рисков и ИСР, переформулирование описания задачи,
семантический индекс и ответы MCP о задачах. В общей аналитике действуют
[правила полноты и бюджета](analytics-context.md). Project Agent перечитывает
задачи из PostgreSQL, чтобы задержка индексации не подменяла актуальные отметки.

## API и хранение

- `POST /api/v1/projects/{project_id}/tasks`: необязательное поле `checklist`.
- `GET /api/v1/tasks/{task_id}` и списки задач: `checklist` и `checklist_revision`.
- `PATCH /api/v1/tasks/{task_id}`: полная замена чек-листа и ожидаемая версия.
- `POST /api/v1/projects/{project_id}/tasks/checklist-suggestion`: multipart,
  поле `payload` с JSON и необязательные повторяющиеся `files`. В JSON — `title`,
  `description_md`, `task_id`, `document_ids`, `checklist`. Результат содержит
  `checklist` и `warnings`; вызов не сохраняет задачу, файлы или предложение.

Пример изменения существующего чек-листа после чтения версии `2`:

```json
{
  "checklist_revision": 2,
  "checklist": {
    "title": "Приёмка",
    "items": [
      {
        "id": "1ba0f9df-5af9-4d8c-bac9-d87ab9cddc91",
        "text": "Согласовать критерии приёмки",
        "is_completed": true
      }
    ]
  }
}
```

UUID пункта сохраняется при правках и перестановке; для нового пункта его можно
не передавать — сервер выдаст UUID. Повторяющиеся UUID отклоняются. Порядок задаётся
массивом. `checklist: null` вместе с версией удаляет чек-лист; отсутствие обоих
полей сохраняет его. Устаревшая версия даёт `409`, неверные данные — `422`.
Обычное изменение других свойств задачи не требует версии чек-листа.

В `tasks` добавлены nullable JSONB `checklist` и целочисленная `checklist_revision`.
Версия увеличивается при каждом принятом PATCH чек-листа. Старые задачи имеют
`NULL` и версию `0`. Изменение, событие `CHECKLIST_CHANGED` и задание переиндексации
сохраняются в одной Unit of Work. SQL и блокировка строки находятся в репозитории;
вызовы LLM, распознавание и файловые операции выполняются вне сессии БД.

Миграция `b8c34dae125f` следует за `a7b23c9d014e`; запуск backend применяет её
через `alembic upgrade head`. Downgrade удаляет данные чек-листов и их версии,
но оставляет метку события в общем PostgreSQL enum, поскольку на неё может
ссылаться история. Для аналитики с новым контекстом старые отчёты нужно пересоздать.

Проверки охватывают CRUD, реальные транзакции и конкурирующие подключения
PostgreSQL, миграцию, доступ, файлы, ошибки и валидацию AI, передачу в аналитику
и индекс. Браузерные сценарии проверяют создание, карточку, конфликт, принятие
предложения и узкий экран. В автоматических проверках ответ AI подменяется.
