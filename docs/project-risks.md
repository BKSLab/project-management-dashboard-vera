# Риски проекта

Реализация `PROJECT_RISKS_IMPLEMENTATION_SPEC.md`. Реестр доступен во вкладке
«Риски» (`/projects/:projectKey/risks`). Риск принадлежит проекту и может быть
связан с одной его задачей. При удалении задачи связь очищается, риск сохраняется.
При удалении участника проекта с его рисков снимается назначение.

## Оценка и состояния

Уровень вычисляет backend по фиксированной матрице. Клиент показывает только
предпросмотр; API запрещает передавать `risk_level`.

| Вероятность / влияние | LOW | MEDIUM | HIGH |
| --- | --- | --- | --- |
| LOW | LOW | LOW | MEDIUM |
| MEDIUM | LOW | MEDIUM | HIGH |
| HIGH | MEDIUM | HIGH | HIGH |

Активными считаются OPEN, MITIGATING и OCCURRED. OCCURRED означает наступившее
событие и остаётся активным до закрытия. CLOSED исключается из активных уровней,
пробелов управления и сигналов внимания. Повторное открытие разрешено.

Стратегия (AVOID, MITIGATE, TRANSFER, ACCEPT) хранится отдельно от двух Markdown-планов:
превентивного `mitigation_plan` и действий при наступлении `response_plan`.
Дата `review_date` — следующий контроль. «Требует контроля» включает сегодня;
«Контроль просрочен» означает дату строго раньше сегодня. Пустой план допускается;
для ACCEPT отсутствие превентивного плана может быть осознанным решением.

Матрица и счётчики охватывают весь отфильтрованный набор независимо от страницы.
По умолчанию интерфейс показывает активные риски. Закрытые можно включить фильтром.
Стабильный ключ `RISK-<id>` использует общий идентификатор реестра.

## HTTP и слои backend

Все URL начинаются с `/api/v1/projects/{project_id}/risks`:

| Метод / суффикс | Результат |
| --- | --- |
| GET / POST | Страница реестра / регистрация риска |
| GET / PATCH / DELETE `/{risk_id}` | Детали / частичное изменение / удаление |
| GET `/summary` | Полные счётчики, 9 ячеек матрицы, reason codes |
| GET `/task-counts` | Активные риски задач одним пакетным запросом для Kanban |
| POST `/suggestions` | До 5 AI-черновиков, без регистрации рисков |

Фильтры: `status`, `probability`, `impact`, `risk_level`, `owner_user_id`, `task_id`,
`search`, `active_only`. Пагинация: `page` от 1, `page_size` от 1 до 100.
`summary` принимает `today` для локальной даты интерфейса. PATCH отличает пропуск
поля от null: null очищает только владельца, задачу или дату контроля.

HTTP/MCP → ProjectRiskService → ProjectRiskRepository → PostgreSQL. Зависимости
передаются через конструкторы и собираются в существующих composition points.
Сервис повторно проверяет доступ, принадлежность задачи и участие владельца.
Изменение риска, обновление времени проекта и outbox индексации коммитятся вместе.
Параллельное редактирование оценки блокирует строку риска и пересчитывает уровень
по актуальной паре probability/impact. Назначение владельца сериализовано с удалением
участника через блокировку строки участия.

## «Пульс», знания и AI

Счётчики и причины внимания доступны проектному и портфельному «Пульсу»:
HIGH_OPEN_RISK, RISK_REVIEW_OVERDUE, RISK_WITHOUT_OWNER,
RISK_WITHOUT_MITIGATION, RISK_OCCURRED. HIGH_OPEN_RISK относится к OPEN/MITIGATING;
реализовавшиеся события имеют отдельный сигнал. Анализ поддерживает проекты,
в которых есть риски, но ещё нет задач. Срез модели ограничен, агрегаты считаются
по всему реестру. Изменение и удаление риска делают прежний анализ устаревшим.

AI-предложения используют ограниченный снимок проекта: задачи, сроки, комментарии,
историю, документы, ИСР, вехи, зависимости и существующие риски. Пользователь может
отклонить предложение или открыть форму, отредактировать её и явно создать запись
с source=AI_SUGGESTED. Неподтверждённые ссылки и дубли по названию отбрасываются.
Чужие/неизвестные ключи задач не превращаются в связи. При недостатке оснований
ответ может быть пустым. Оценки модели остаются предложением для проверки человеком.

Сервис закрывает всю DB-область, включая авторизацию, до обращения к LLM.
Используются существующие AI-клиенты и настройки провайдера.

Риски индексируются существующим KnowledgeIndexService через transactional outbox.
В Qdrant помещаются название, описание и оба плана. Полная переиндексация включает
реестр. У фрагментов риска нет `task_id` в payload: удаление контекста задачи не должно
удалять независимый риск. Project Agent перепроверяет найденные риски пакетным запросом
PostgreSQL, исключает исчезнувшие записи и использует текущие поля. Источник ответа
открывает Risk Drawer. Отдельный SQL-инструмент агента `list_project_risks` читает
реестр и точные счётчики; прежние календарные сигналы остаются отдельным инструментом.

## MCP

`list_project_risks`, `get_project_risk`, `create_project_risk`, `update_project_risk`
используют тот же ProjectRiskService. Проект и риск задаются ключами PROJ и RISK-12,
задача — PROJ-142, ответственный — логином участника. Списки ограничены страницей,
длинные тексты явно отмечаются `truncated_fields`.

Для создания и изменения нужен токен с правом записи и обязательный
`confirmed_by_user=true`: вызывающий агент передаёт его только после подтверждения
человеком конкретных полей. Это контракт инструмента, а не независимая проверка
факта согласия. Пустые строки `owner`, `task_key`, `review_date` в update очищают
ссылки/дату; пропущенные поля сохраняются. Источник и вычисляемый уровень не редактируются.

## Миграции и проверка

Перед запуском новой версии backend выполнить из `backend`:

```shell
python -m alembic upgrade head
```

Миграция `f6a12b8c903d` создаёт таблицу и собственные enum-типы.
`a7b23c9d014e` добавляет RISK в общий `knowledge_entity_type`.
Откат удаляет таблицу и её собственные типы, сохраняя прежние данные проекта.
Общая enum-метка RISK при откате остаётся: PostgreSQL не поддерживает DROP VALUE,
а переписывать или удалять outbox в schema-only миграции нельзя. Перед эксплуатацией
старого worker после отката следует завершить обработку заданий RISK новой версией;
старый worker не знает эту метку. Сам откат таблицы удаляет зарегистрированные риски.

Проверки:

```shell
# backend: PostgreSQL и Qdrant запускаются тестами в Docker
python -m pytest -q
python -m ruff check src tests

# frontend
npm run build
npm run lint
npm test
npx playwright install chromium
npm run test:e2e
```

В Windows можно использовать установленный Edge:
`$env:PLAYWRIGHT_CHANNEL = 'msedge'` перед `npm run test:e2e`.
Браузерные сценарии подменяют API и не изменяют рабочие данные.
Миграции проверяются на отдельной базе тестового контейнера PostgreSQL, включая
upgrade, downgrade, повторный upgrade, индексы, ограничения и сохранность прежних записей.
Интеграционные тесты проверяют также FK и атомарность риска с outbox.

Календарные маркеры контроля остаются предусмотренным спецификацией последующим
расширением. Универсального audit-механизма в проекте нет; отдельная система истории
рисков не создавалась. Доступная история TaskActivity относится только к задачам.
