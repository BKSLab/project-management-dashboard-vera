# Инструкции для работы с проектом

## С чего начинать

- Прочитай [MEMORY.md](MEMORY.md): текущее состояние и согласованные границы.
- Запуск, настройки и карта документации — в [README.md](README.md).
- Для backend действуют [FASTAPI_PATTERNS.md](FASTAPI_PATTERNS.md), для UI —
  [docs/DESIGN_GUIDE.md](docs/DESIGN_GUIDE.md). Читай остальные документы по задаче.
- Сначала проверь `git status` и относящийся к задаче diff. Существующие
  незакоммиченные изменения переноса нужно сохранять.

## Границы личного проекта

- Помощника зовут Вера; её роль — проектный менеджер. В проекте одна вкладка
  «Чат» с обращением «Вера, …». Личные диалоги остаются приватными.
- Используются локальные пользователи, регистрация по коду приглашения,
  cookie/JWT и собственные API-ключи. Корпоративные SSO, SD, staff/company
  роли, PM-agent, обращения и встраивание в чужой интерфейс сюда не входят.
- Не добавляй потоки/flows и учёт времени — ни модели, ни поля, ни инструменты,
  ни пункты меню. Загрузка календаря считается по числу задач.
- Файлы сохраняются локально. Извлечение текста документов и таблиц выполняет
  код проекта. Для изображений сохранён настраиваемый vision API;
  корпоративные storage, извлечение текста/OCR и OCR сканов PDF не подключать.
- Не добавляй Phoenix/OpenInference/OTLP-экспорт, корпоративный health/heartbeat,
  доверенные SSO-заголовки, корпоративные deploy jobs и служебные каталоги.
- PostgreSQL, Redis, Qdrant и настроенные LLM/embeddings/vision — зависимости
  этого приложения; их конфигурацию нельзя подменять настройками другого проекта.
- Для LLM-диагностики используй только текущий ключ этого проекта. Нельзя
  брать, копировать или использовать ключи рабочего и других проектов даже
  для сравнительного запроса. Их код и несекретные параметры можно сравнивать.

## Правила изменения кода

- HTTP, MCP и инструменты агента используют общие сервисы и одинаковые
  доменные права. Не добавляй обходов доступа в отдельном канале.
- Сохраняй совместимость прежних `tt_` READ/WRITE-токенов и `/mcp`.
  `ttk_`-ключи ограничены scopes и доступом своего локального владельца.
- ORM `User` хранит части ФИО; не копируй предположения о корпоративном User
  или иной форме `Principal`. Автор и права определяются сервером.
- ИСР и свободная доска — разные подсистемы. Три состояния размещения задачи
  и правила безопасного удаления описаны в [docs/wbs.md](docs/wbs.md).
- Перенос задачи сохраняет историю, вложения и отчёты; связи прежнего
  проектного контекста снимаются одной транзакцией через общий сервис.
- Runtime агента обязан сохранять WriteGate, отдельное подтверждение опасных
  действий, квитанции повторов и повторную проверку актуального доступа.
- Миграции добавляются поверх существующей цепочки Alembic. Не заменяй base,
  не пересоздавай БД и не удаляй данные ради обновления схемы.
- В UI используй существующие токены, тёмную тему и единую оболочку P.
  Не копируй корпоративные палитры и дополнительные оболочки.

## Проверки и сдача

- По умолчанию: понять → изменить → проверить → просмотреть diff. Не запускай
  полный процесс и все тесты для небольшой правки документации.
- Команды проверок находятся в README; правила тестов — в
  [backend/tests/README.md](backend/tests/README.md). Интеграционные тесты требуют
  Docker и настоящего PostgreSQL; пропуск не считается успешной проверкой.
- Проверяй затронутое поведение. Полный прогон повторяй при широком влиянии
  или конкретном риске; успешные проверки не повторяй без изменения их входов.
- Делегируй независимые участки, когда это экономит время: передавай точные
  пути, ограничения и критерий результата, обычно без всей истории.
- Отчёт — коротко по-русски: результат, проверки и реальные ограничения.
  Не выдавай mock-проверку за вызов настоящего LLM или работу UI с живым API.

## Данные и документация

- Не печатай содержимое `.env`, секреты, токены, пароли и приватные данные.
- Не удаляй `data/uploads` и Docker volumes. Обновлению существующей БД
  должна предшествовать резервная копия; `docker compose down -v` здесь не применять.
- `.claude/worktrees` содержит отдельные checkout: не меняй и не очищай их
  вместе с текущим проектом без отдельного поручения.
- Коммит, push и внешние сообщения требуют конкретного разрешения пользователя.
- В MEMORY обновляй текущие факты и дату проверки; не превращай её в журнал.
  Для подсистемы поддерживай одно актуальное описание, не новые параллельные
  планы, отчёты ревью и копии каталога API.
