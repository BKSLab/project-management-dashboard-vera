# Project Task Tracker

Трекер задач, построенный вокруг проекта: дашборд по всем проектам, канбан, список задач, иерархическая структура работ (ИСР) и проектные документы в одном интерфейсе.

Проект — корневая сущность. Задачи, стадии канбана, документы и статистика существуют только внутри проекта. Без входа не доступно ничего, а вошедший пользователь видит только свои проекты.

## Текущее состояние

Реализовано и работает:

- регистрация по логину и паролю с кодом приглашения, вход и выход, профиль с ФИО, фотографией и контактами;
- изоляция данных: пользователь видит и правит только проекты, в которых состоит;
- общий дашборд: показатели портфеля, карточки проектов с прогрессом, просроченные задачи и лента изменений;
- проекты: создание, настройка, статусы, цвет и иконка, удаление вместе со всем содержимым;
- канбан проекта со своими стадиями, drag-and-drop и оптимистичным откатом при ошибке;
- список задач таблицей с фильтрами по стадии и приоритету;
- единая карточка задачи в правой панели: свойства, описание, документы, файлы, комментарии и история;
- сквозные номера задач вида `VERA-142` и поиск по тексту, комментарию и номеру;
- документы проекта с Markdown-редактором, полнотекстовым поиском и связями с задачами;
- интерактивный конструктор ИСР: canvas с автоматической раскладкой, пул нераспределённых задач, drag & drop, semantic zoom, minimap и поиск;
- миграции Alembic и подробное логирование backend-запросов;
- API v1 с OpenAPI/Swagger по адресу `/docs`.

## Доменная модель

```text
User
├── owned_projects   → Project.owner_id
└── memberships      → ProjectMember

Project
├── owner_id          владелец: единственный, кто может удалить проект
├── members           участие, через которое проверяется весь доступ
├── ProjectStage      колонки канбана этого проекта
├── Task              project_id, stage_id, number → VERA-142
│   ├── TaskComment
│   ├── TaskActivity
│   └── TaskAttachment
├── WbsNode           структурный контейнер ИСР
└── Document ── DocumentLink ── Task
```

Ключевые правила:

- доступ к проекту и всему его содержимому определяется участием в проекте;
- чужой объект отдаёт 404, а не 403: существование чужих данных не подтверждается;
- задача принадлежит ровно одному проекту, её стадия — из того же проекта;
- `Task.wbs_node_id` необязателен: `NULL` означает «задача не распределена по структуре»;
- `WbsNode` — контейнер, а не задача: у него нет статуса, приоритета и срока;
- номера ИСР (`1`, `1.1`, `1.2.1`) не хранятся, а вычисляются из `parent_id` и `position`;
- координаты узлов на карте тоже не хранятся: раскладку считает frontend;
- удаление раздела никогда не удаляет задачи — они возвращаются в пул нераспределённых.

## Архитектура

Backend следует слоистой схеме:

```text
HTTP endpoint → service → repository → PostgreSQL
                       ↘ storage → локальный диск
```

- `api/v1/endpoints` — HTTP-контракт, OpenAPI, преобразование доменных ошибок в ответы;
- `services` — бизнес-сценарии и сборка данных из нескольких репозиториев;
- `repositories` — SQLAlchemy-запросы, транзакции и преобразование ошибок БД;
- `db/models` — одна SQLAlchemy-модель на файл;
- `schemas` — Pydantic-схемы запросов и ответов;
- `dependencies` — трёхуровневый граф FastAPI Depends;
- `exceptions` — отдельная иерархия ошибок для каждого домена;
- `src/main.py` — FastAPI-приложение, lifespan, CORS и системные обработчики ошибок;
- `main.py` — совместимая точка входа для `hypercorn main:app`.

Правила backend-архитектуры зафиксированы в [`FASTAPI_PATTERNS.md`](FASTAPI_PATTERNS.md).

Frontend построен на React 19, TypeScript, Vite, Tailwind CSS v4, TanStack Query, Zustand и `@dnd-kit`. Иконки — `lucide-react`. Адреса API и ключи кэша собраны в `frontend/src/lib/api.ts`: локально используется `http://localhost:8000`, Docker-сборка обращается к API через относительный путь.

## Конструктор ИСР

Раздел «Структура» реализован по [`docs/WBS_BUILDER_SPEC.md`](docs/WBS_BUILDER_SPEC.md).

Слева — пул задач: по умолчанию нераспределённые, переключатель «Все» помогает найти уже размещённую задачу. Справа — canvas на `@xyflow/react` с автоматической раскладкой `elkjs` в горизонтальном и вертикальном режимах.

Что важно в модели:

- пользователь не расставляет блоки: координаты вычисляются раскладкой и не хранятся;
- пользователь не рисует связи: рёбра выводятся из `parent_id` и `wbs_node_id`;
- номера разделов вычисляются из позиции в дереве и меняются сразу после переноса;
- прогресс раздела агрегирует задачи всех потомков и не хранится отдельно;
- удаление раздела возвращает задачи в пул и никогда их не удаляет.

Взаимодействия: перетаскивание задачи из пула на раздел и обратно, перенос разделов с зонами «перед», «внутрь» и «после», сворачивание веток, semantic zoom (при сильном отдалении отдельные задачи скрываются и остаётся архитектура проекта), поиск с раскрытием пути и центрированием, minimap. Всё, что делается мышью, доступно и через контекстное меню с диалогами «Переместить…» — drag & drop не единственный способ управления.

Структура загружается одним запросом `GET /projects/{id}/wbs`; изменения применяются оптимистично и откатываются с уведомлением, если сервер отказал.

## Поиск

Векторный поиск хранится непосредственно в PostgreSQL в вычисляемых `tsvector`-полях:

| Сущность | Поля поиска | Приоритет |
|---|---|---|
| Проект | `name`, `description_md` | название выше описания |
| Задача | `title`, `description_md` | заголовок выше описания |
| Комментарий | `body_md`, `author_name` | текст выше автора |
| Документ | `title`, `content_md` | заголовок выше содержимого |

Для каждого вектора создан GIN-индекс. Запрос строится через `websearch_to_tsquery`; для обычного текста дополнительно поддерживается безопасный префиксный поиск от трёх символов, поэтому `пользова` находит формы слова «пользователь». Спецсимволы не приводят к синтаксическим ошибкам. Поиск задач дополнительно понимает номер: находит и по `VERA-142`, и по `142`. Backend формирует фрагменты через `ts_headline`, а frontend выделяет совпадения акцентным цветом.

## Локальный запуск

### PostgreSQL и backend

Требуется Python 3.12 и доступный PostgreSQL 16.

```powershell
cd backend
python -m venv venv
.\venv\Scripts\Activate.ps1
pip install -r requirements-dev.txt
```

Заполните `backend/.env`, затем выполните:

```powershell
alembic upgrade head
hypercorn main:app
```

Backend доступен на `http://127.0.0.1:8000`:

- Swagger UI: `http://127.0.0.1:8000/docs`;
- OpenAPI: `http://127.0.0.1:8000/openapi.json`;
- API: `http://127.0.0.1:8000/api/v1`.

Начальных данных нет. Сначала зарегистрируйтесь на `/register`, указав код приглашения из `REGISTRATION_INVITE_CODE`. Первый проект создаётся через интерфейс, вместе с ним автоматически появляется канбан со стадиями Бэклог, В работе, Ревью, Тестирование и Готово.

В `backend/.env` должны быть заданы `JWT_SECRET` и `REGISTRATION_INVITE_CODE` — без них приложение не стартует, чтобы не уехать в прод с общеизвестным ключом. За TLS дополнительно включите `SESSION_COOKIE_SECURE=true`.

Каждый вызов endpoint-а пишет в консоль начало и успешное завершение запроса. Если сервер стартовал, но запросов в логах нет, проверьте, какой процесс занимает порт:

```powershell
Get-NetTCPConnection -LocalPort 8000 -State Listen
```

### Frontend

```powershell
cd frontend
npm install
npm run dev
```

Vite по умолчанию откроет `http://localhost:5173`. Frontend не требует `.env`: при локальном запуске backend ожидается на `http://localhost:8000`.

## Запуск через Docker Compose

```bash
docker compose up -d --build
```

PostgreSQL и backend используют единый файл `backend/.env`. Для Docker в нём должны быть активны `POSTGRES_HOST=db`, `POSTGRES_PORT=5432`, `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_NAME` и `POSTGRES_DB`.

После запуска интерфейс доступен на `http://<хост>:93/`.

| Сервис | Назначение | Порт хоста |
|---|---|---|
| `db` | PostgreSQL 16 | `5436` |
| `backend` | FastAPI/Hypercorn | только внутренняя сеть |
| `frontend` | собранная Vite-статика | только внутренняя сеть |
| `nginx` | frontend и proxy `/api/` | `93` |

`backend/entrypoint.sh` применяет `alembic upgrade head` и запускает Hypercorn с access/error logs в stdout.

Файлы задач сохраняются на хосте в `data/uploads` и монтируются в backend как `/app/uploads`. Каталог не входит в Git и сохраняется при пересоздании контейнера. Для полного резервного копирования нужны одновременно дамп PostgreSQL и каталог `data/uploads`.

## Файлы задач

К задаче можно прикрепить до 20 файлов размером до 10 МБ каждый. Поддерживаются изображения, PDF, документы Office, текстовые файлы и распространённые архивы. SVG, HTML и исполняемые файлы не принимаются.

В PostgreSQL хранятся исходное имя, MIME-тип, размер и уникальный storage key. Физическое содержимое находится в `data/uploads/tasks/<task_id>/`; безопасное растровое изображение показывается inline, остальные типы выдаются для скачивания. При удалении задачи или проекта удаляются и метаданные, и физические каталоги файлов.

Миниатюра изображения открывает отдельный preview поверх карточки задачи; из него доступны скачивание и открытие оригинала. Для маршрутов загрузки и выдачи вложений nginx отключает временное request/response buffering и передаёт данные потоком.

## Аутентификация

Вход выполняется по логину: подтверждения почты нет, поэтому email остаётся необязательным контактом. Пароль хранится bcrypt-хешем и никогда не возвращается в API.

Сессия живёт в httpOnly cookie с `SameSite=Lax`: токен недоступен из JavaScript, а Lax закрывает CSRF, потому что браузер не отправит такую cookie при кросс-сайтовых `POST`, `PATCH` и `DELETE`.

Регистрация закрыта кодом приглашения из переменной окружения — сайт открыт наружу, и без кода посторонний не заведёт себе учётную запись. Ответ на неверный логин и на неверный пароль одинаков, иначе существующие логины можно перебирать.

Доступ проверяется в Depends-слое по правилу из `FASTAPI_PATTERNS.md`. Роли участия: `OWNER` может всё, включая удаление проекта; `MEMBER` ведёт задачи, ИСР и документы, но проект не удаляет.

## Осознанные ограничения

- исполнитель задачи — свободное текстовое поле, а не ссылка на пользователя;
- нет восстановления пароля, подтверждения почты и ограничения частоты попыток входа;
- приглашения в команду проекта по ссылке пока не сделаны: фундамент под них заложен;
- внешние API и LLM-клиенты отсутствуют;
- списки задач, стадий и структура ИСР возвращаются целиком: frontend строит полное состояние доски и дерева;
- Hunspell и автоматическое исправление опечаток через `pg_trgm` пока не подключены;
- конструктор ИСР вынесен в отдельный чанк, но сам по себе весит около 513 КБ gzip из-за React Flow и elkjs;
- автотестов интерфейса нет: проверки браузером выполнялись вручную.
