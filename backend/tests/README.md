# Тесты backend: как они устроены и что сюда добавлять

Набор проверяет поведение и границы, а не число тестов. Один тест — одно
правило или один use case со всеми его случаями внутри.

## Разделы

| Каталог | Что проверяет | Чем ценен |
|---|---|---|
| `architecture/` | Направление зависимостей, контракт репозиториев, граф маршрутов | Ловит то, что не ломает ни один сценарный тест: репозиторий в эндпоинте, `get_settings()` в сервисе, маршрут без проверки прав |
| `unit/` | Поведение сервисов, клиентов, MCP-инструментов, воркера | Быстрая проверка алгоритмов и доменных правил на дублёрах |
| `api/` | HTTP-контур: коды ответов, валидация, multipart, стриминг | Проверяет транспорт, а не бизнес-логику за ним |
| `integration/` | Реальный PostgreSQL: транзакции, каскады, серверные значения, конкурентный захват очереди | Единственное место, где проверяется настоящее поведение базы |
| `characterization/` | Снимок публичного контракта HTTP и MCP | Защита от молчаливого изменения API |

## Что добавлять

Новый тест нужен, если верно хотя бы одно:

- он закрепляет **контракт**: URL, метод, статус, форму ответа, формат
  MCP-инструмента, правило прав, границу транзакции;
- он покрывает **нетривиальный алгоритм**: расчёт позиций и уплотнение,
  выделение цикла в ИСР, чанкинг, backoff, перенос дат, дедупликацию
  очереди;
- он ловит **регрессию, которую больше никто не поймает**: архитектурный
  guard, поведение на реальном PostgreSQL, компенсацию внешнего файла.

## Чего не добавлять

- Тест, проверяющий, что сервис вызвал репозиторий с такими-то
  аргументами, когда результат уже закреплён api- или
  integration-тестом. Такой тест падает при безобидном рефакторинге и
  молчит при настоящей ошибке.
- Отдельный тест на каждое значение одного правила. Правило проверяется
  один раз прогоном по всем случаям.
- Повтор того, что уже закреплено на другом слое.

## Форма проверки правила

Правило по набору объектов пишется одним тестом, который собирает все
нарушения и показывает их разом:

```python
def test_service_never_reads_global_settings() -> None:
    offenders = [
        f"{path}:{line}"
        for path in iter_python_files("services")
        for line in calls_named(parse(path), "get_settings")
    ]
    assert not offenders, "get_settings() в сервисах: " + ", ".join(offenders)
```

Так добавление файла или ресурса не добавляет тестов, а падение сразу
называет все места, где правило нарушено. Параметризация оставлена лишь
там, где случай действительно самостоятельный.

## Границы объединения

Тесты одного use case объединяются в один; docstring исходной проверки
остаётся комментарием над своим блоком.

Не объединяются:

- **тесты, зависящие от состояния базы.** В `integration/` сценарий видит
  строки, записанные предыдущим: счётчики и выборки перестают совпадать.
  Изоляция здесь важнее числа тестов;
- **тесты жизненного цикла приложения** (`unit/test_main.py`): они
  проверяют события и задачи, которые нельзя дважды взвести в одном
  прогоне;
- **параметризованные тесты, где случай — самостоятельная единица**
  (например, отображение статусов HTTP на решение о повторе).

## Команды

Из каталога `backend`:

```powershell
.\venv\Scripts\ruff.exe check src tests
.\venv\Scripts\python.exe -m pytest -q --cov=src --cov-report=term
```

Покрытие `src` не должно опускаться ниже 78%: это ограничитель, который
не даёт сокращать набор за счёт настоящих проверок. Перед
`tests/integration` нужен доступный Docker: локальный `skip`
testcontainers успешной проверкой не считается.
