# Записка для ревью: переход на модель «проект — корневая сущность»

Документ описывает, что и почему изменено в ветке `feat/project-first`, что уже проверено, а что нет, и на какие места стоит смотреть внимательнее. Он не заменяет `README.md` (как устроено сейчас) и `docs/PROJECT_DASHBOARD_PLAN.md` (архитектура) — здесь только контекст изменения.

## 1. Что было и что стало

**Было.** Трекер обслуживал один проект «Агент Вера». Задачи, стадии канбана, документы и статистика жили глобально. Иерархия работ была отдельной сущностью `WbsItem` (247 узлов из seed-снэпшота), у каждого листа которой создавалась своя карточка канбана; две структуры синхронизировались вручную в `WbsService`.

**Стало.** `Project` — корневая сущность. Задачи, стадии, документы и статистика существуют только внутри проекта. ИСР перестроена: `WbsNode` — чистый структурный контейнер, задача ссылается на него через nullable `wbs_node_id`. Появились общий дашборд по портфелю и интерактивный конструктор ИСР.

Объём: 4 коммита, 214 файлов, +19139 / −12729 строк, 82 файла добавлено, 69 удалено.

```text
3242148  backend: доменная модель, API, тесты
5736362  frontend: дизайн-система и экраны
9a002c5  docs: README и архитектурный обзор
1b8f877  frontend: конструктор ИСР + найденные при проверке исправления
```

## 2. Требования, по которым сделано

Три документа, все обязательны и все соблюдены:

- `FASTAPI_PATTERNS.md` — слоистая архитектура backend, стиль кода, пирамида тестов;
- `docs/DESIGN_GUIDE.md` — токены, компоненты, состояния, доступность;
- `docs/WBS_BUILDER_SPEC.md` — ТЗ на конструктор ИСР.

Решения, принятые до начала работ и согласованные с заказчиком:

| Развилка | Решение |
|---|---|
| Существующие данные | Чистый старт: seed-скрипты и снэпшот ИСР удалены, схема пересоздана |
| Иерархия | Только `WbsNode`; у задачи нет `parent_id` — §51 ТЗ запрещает структурные задачи-заглушки |
| Стадии канбана | Свои у каждого проекта, копируются из шаблона при создании |
| Документы | Принадлежат проекту, `slug` уникален внутри проекта |
| Палитра | Строго по `docs/DESIGN_GUIDE.md` (GitHub Dark), без смешивания с другими темами |
| Карточка задачи | Правая панель (§37 ТЗ и §11 гайда), единая для канбана, списка и структуры |

## 3. Доменная модель

```text
Project
├── ProjectStage      колонки канбана этого проекта
├── Task              project_id, stage_id, wbs_node_id, number → VERA-142
│   ├── TaskComment
│   ├── TaskActivity
│   └── TaskAttachment
├── WbsNode           структурный контейнер ИСР
└── Document ── DocumentLink ── Task
```

Удалены: `WbsItem`, `SeedState`, `KanbanStage`, `KanbanTask`. Девять миграций заменены одной начальной (`20260901_1200_project_first_schema.py`).

### Что намеренно НЕ хранится

Это осознанные решения, а не упущения:

- **номера ИСР** (`1`, `1.1`, `1.2.1`) — вычисляются из `parent_id` и `position` в `frontend/src/lib/wbsTree.ts`. Хранить их значило бы поддерживать консистентность при каждом переносе;
- **координаты узлов на карте** — считает `elkjs`, §17 ТЗ прямо запрещает хранить `x`/`y` как бизнес-данные;
- **прогресс раздела** — агрегируется из задач поддерева на клиенте (§47 ТЗ).

**Номер задачи, наоборот, хранится** (`Task.number`): он попадает в ссылки и обсуждения и не должен меняться при перестановке.

### Инварианты в сервисном слое

БД не может их выразить, поэтому они живут в сервисах — при ревью стоит проверить именно там:

| Инвариант | Где |
|---|---|
| стадия задачи из того же проекта | `services/tasks.py::_resolve_stage_id`, `move_task` |
| раздел ИСР из того же проекта | `services/tasks.py::_ensure_wbs_node_in_project`, `services/wbs_nodes.py::_change_task_assignment` |
| нет циклов в структуре | `services/wbs_nodes.py::_ensure_no_cycle` |
| удаление раздела не удаляет задачи | `services/wbs_nodes.py::delete_node` |
| документ и задача одного проекта | `services/document_links.py::create_link` |
| последнюю и непустую стадию не удалить | `services/project_stages.py::delete_stage` |

## 4. Позиционирование: почему так

Порядок задач в стадии и разделов на уровне — разреженная шкала с шагом 1000.

**Backend полностью владеет расчётом позиции.** Клиент передаёт только «нового родителя» и «соседа, перед которым встать» (`POST /wbs/nodes/{id}/move` с `{parent_id, before_id}`), а не готовое число. Это требование §10 ТЗ: frontend не должен воспроизводить persistence-логику сортировки.

Когда промежуток между соседями исчерпан (`< 0.001`), `services/wbs_nodes.py::_compact_positions` уплотняет весь уровень одной транзакцией. Логика вставки вынесена в чистую функцию `_next_position` и покрыта тестами.

На клиенте есть `predictPosition` в `lib/useWbsMutations.ts` — он нужен **только** чтобы оптимистичный шаг не переставил узлы визуально; итоговое значение берётся из ответа сервера в `onSuccess`.

## 5. Статистика: почему без N+1

`GET /dashboard` считает портфель тремя агрегатными запросами независимо от числа проектов:

- `TasksRepository.get_portfolio_counters` — total / done / overdue / due_soon / next_due_date по проектам одним `GROUP BY` с `FILTER`;
- `get_stage_counts` — разбивка по стадиям;
- `get_attention_tasks` — задачи с ближайшими сроками.

`ProjectStatsSchema` для одного проекта считается в памяти из его стадий и задач (`services/projects.py::build_project_stats`) — это чистая функция, покрытая тестами.

## 6. Frontend

### Разделение состояния (§53 ТЗ)

- **server state** — TanStack Query, ключи и адреса собраны в `lib/api.ts`;
- **derived state** — дерево, номера, прогресс, граф и координаты: `lib/wbsTree.ts`, `lib/wbsLayout.ts`;
- **UI state** — Zustand `stores/ui.ts`: выбранная задача, сайдбар, свёрнутые ветки, режим раскладки.

### Дизайн-система

Все токены — в `frontend/src/app.css`, локальные HEX в компонентах не допускаются (§21.11 гайда). Базовые компоненты в `components/ui/`. Иконки — единый набор `lucide-react` (§15).

Одна задача имеет одно представление везде: карточка канбана, строка списка и узел структуры используют одни токены статуса и приоритета и открывают одну и ту же панель `components/tasks/TaskDrawer.tsx`.

### Конструктор ИСР

Раскладка пересчитывается **только при смене топологии графа или режима** — ключ `topologyKey` в `StructureCanvas.tsx`. Hover, выделение и открытие панели задачи layout не трогают (§43 ТЗ). Данные узлов обновляются отдельным `useMemo`, чтобы изменение прогресса не перезапускало elk.

Модуль вынесен в отдельный чанк через `React.lazy` в `App.tsx`: React Flow и elkjs весят ~513 КБ gzip и не должны попадать в стартовый бандл (он остался 213 КБ).

## 7. Дефекты, найденные при проверке в браузере

Проверка живого интерфейса нашла то, чего не видели типизация, линтер и юнит-тесты. Все исправления в коммите `1b8f877`.

1. **Падение canvas после удаления раздела.** Между удалением и пересчётом раскладки узел ещё жил в `flowNodes`, а в `tree.byId` его уже не было. Код возвращал такой узел с пустым `data`, и `SectionNode` падал на `section.node`. Исправление: `decoratedNodes` стал `flatMap` и отбрасывает нерезолвящиеся узлы, `visibleEdges` — рёбра без обоих концов.

2. **Терялся drop задачи из пула.** `handleDrop` полагался на `draggingTask`, выставляемый в `dragstart`. Если события приходят в одном кадре, React ещё не перерисовался и состояние было `null`. Исправление: идентификатор задачи читается из `event.dataTransfer` — для этого он там и лежит. Состояние осталось только для визуальной подсказки.

3. **Смена режима раскладки не возвращала граф в кадр** — добавлен `fitView` при изменении режима (по `layoutModeRef`).

4. **Backend: `clear_wbs_node` не синхронизировал identity map.** Массовый `UPDATE` шёл с `synchronize_session=False`, поэтому уже загруженные в сессию задачи сохраняли устаревший `wbs_node_id`. В проде каждый запрос получает свежую сессию, но полагаться на это хрупко — заменено на `synchronize_session="fetch"`.

5. Мелочи: фильтры пула не помещались в колонку, отсутствовал favicon (404 в консоли), полоса прогресса в шапке проекта висела оторванно от заголовка.

Отдельно: фикстура `engine` в `tests/conftest.py` была сессионной и падала при доступном Docker — asyncpg привязывает соединения к event loop, а pytest-asyncio даёт каждому тесту свой цикл. Сделана пофункциональной, контейнер остался общим на прогон. Раньше это не проявлялось, потому что integration-тесты просто пропускались.

## 9. Что НЕ проверено и не сделано

Честно, чтобы ревьюер не искал того, чего нет:

- **автотестов интерфейса нет.** Браузерная проверка была ручной: Playwright ставился временно, драйвил системный Edge и удалён вместе со скриптами. Причина — в репозитории нет CI, а тест, требующий установленный браузер, работал бы не у всех;
- **массовое распределение задач** из пула (§32 ТЗ) не сделано — само ТЗ выносит его во вторую итерацию;
- **Docker Compose не пересобирался** после изменений: проверка шла на локальном Postgres в контейнере и `hypercorn` напрямую. `docker-compose.yml` и `nginx.conf` не менялись, но полный `docker compose up --build` не прогонялся;
- **нагрузка не проверялась**: структура и список задач возвращаются целиком, это осознанное ограничение (frontend строит полное состояние дерева и доски);
- **миграция написана вручную**, а не через `--autogenerate`: на момент написания БД не была доступна. Соответствие подтверждено `alembic check` позже.

## 10. Куда смотреть внимательнее

Места, где ошибка была бы дороже всего:

1. `services/wbs_nodes.py` — расчёт позиций, уплотнение уровня, проверка циклов, освобождение задач при удалении. Здесь же `_next_position` и `_collect_subtree_ids`.
2. `repositories/tasks.py::get_portfolio_counters` — условная агрегация с `FILTER`; ошибка здесь тихо исказит весь дашборд.
3. `services/tasks.py::_save_with_number` — выдача номера с повтором при гонке за уникальным ограничением.
4. `components/wbs/StructureCanvas.tsx` — `decoratedNodes`, `visibleEdges` и `topologyKey`: именно здесь были найденные падение и лишние пересчёты.
5. `lib/useWbsMutations.ts` — оптимистичные обновления и откаты: расхождение с сервером проявится не сразу.
6. Каскады удаления: `Project → Task/WbsNode/Document`, `WbsNode → children`, `Task.wbs_node_id → SET NULL`. Проверены integration-тестами, но цена ошибки высока.

## 11. Как запустить и проверить

```powershell
# БД (если нет локального PostgreSQL): контейнер на параметрах из backend/.env
docker run -d --name tracker_pg_dev -e POSTGRES_USER=... -e POSTGRES_PASSWORD=... `
  -e POSTGRES_DB=project_management_dashboard_vera -p 5432:5432 postgres:16-alpine

cd backend
.\venv\Scripts\Activate.ps1
alembic upgrade head
ruff check . ; ruff format --check . ; flake8 . ; alembic check ; pytest -q
hypercorn main:app

# в другом окне
cd frontend
npm install
npm run lint ; npm test ; npm run build
npm run dev
```

Начальных данных нет: первый проект создаётся через интерфейс, стадии канбана появляются автоматически.

**В базе разработчика на момент передачи остались демо-данные** — проекты «Агент Вера» (10 задач, 6 разделов) и «Корпоративный сайт». Они создавались для проверки конструктора и удаляются через настройки проекта.
