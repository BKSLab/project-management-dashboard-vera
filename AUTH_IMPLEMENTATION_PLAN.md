# План: пользователи, аутентификация и изоляция проектов

Документ описывает, что делаем в этом заходе, какие решения приняты и почему, и в каком порядке идём. После выполнения план останется как запись принятых решений.

## 1. Задача

Сейчас трекер полностью открыт: любой, кто дошёл до адреса, видит и правит все проекты. В `README.md` и `docs/PROJECT_DASHBOARD_PLAN.md` это зафиксировано как осознанное ограничение — «авторизация не входит в текущий контур и не должна добавляться без отдельного решения». Настоящий документ и есть это решение.

Что должно получиться:

- регистрация по логину и паролю, пароль вводится дважды;
- подтверждения почты нет — сервис пока личный;
- **без входа не видно ничего**, включая дашборд;
- вошедший видит **только свои проекты**;
- карточка пользователя сразу нормальная: ФИО по полям (отчество необязательно), фотография, почта, телефон, Telegram.

## 2. Принятые решения

| Развилка | Решение | Почему так |
|---|---|---|
| Идентификатор входа | Отдельный логин (`username`) | Соответствует формулировке «логин и пароль»; почта остаётся необязательным контактом и не требует подтверждения |
| Хранение токена | JWT в httpOnly cookie, `SameSite=Lax` | JavaScript до токена не дотянется, значит XSS его не украдёт. `localhost:5173` и `localhost:8000` считаются одним сайтом, поэтому работает и локально, и за nginx |
| Кто может зарегистрироваться | По коду приглашения из переменной окружения | Сайт открыт на порту 93. Одна строка в `.env` закрывает чужие регистрации, но не мешает завести аккаунт кому нужно |
| Существующие проекты | Удаляются миграцией | В базе только демо-данные, созданные при проверке конструктора ИСР. Чистая миграция без переходных состояний |
| Модель доступа | Членство в проекте (`ProjectMember`), не просто `owner_id` | Дальше планируются приглашения в команду по ссылке. Контроль доступа тяжелее всего переделывать задним числом, поэтому закладываем его сразу |
| Права участника | Всё, кроме удаления проекта | Две роли: `OWNER` и `MEMBER`. Необратимое действие остаётся только у владельца |
| Объём по команде | Сейчас только фундамент | Таблица участников и проверки через членство. Приглашения по ссылке — следующий заход, он не потребует ни миграций, ни переписывания проверок |

Отдельно: вместо `passlib` берём `bcrypt` напрямую. `passlib==1.7.4` несовместим с `bcrypt>=4.1` и на каждом хешировании пишет в лог трассировку `AttributeError: module 'bcrypt' has no attribute '__about__'`. Хеширование — шесть строк, промежуточный слой того не стоит.

## 3. Модель данных

```text
User
├── owned_projects   → Project.owner_id
└── memberships      → ProjectMember

Project
├── owner_id         → User            (кто владеет, единственный)
└── members          → ProjectMember   (кто имеет доступ, включая владельца)
```

### User

`username` (уникален, индекс), `password_hash`, `last_name`, `first_name`, `middle_name` (nullable), `email` (nullable), `phone` (nullable), `telegram` (nullable), `avatar_key` (nullable), `is_active`, таймстемпы.

Почта необязательна и **не уникальна**: она контакт, а не идентификатор. Если позже понадобится восстановление пароля, уникальность добавится отдельной миграцией вместе с подтверждением.

### ProjectMember

`project_id`, `user_id`, `role` (`OWNER` / `MEMBER`), `created_at`, `UniqueConstraint(project_id, user_id)`.

Владелец при создании проекта сразу получает строку с ролью `OWNER`. Это значит, что проверка доступа везде одна и та же — «есть ли строка участия», — и приглашённый участник ничем не отличается от владельца с точки зрения выборок.

### Project

Добавляется `owner_id` (FK `users`, `NOT NULL`, `ondelete=CASCADE`). Удаление пользователя уносит его проекты со всем содержимым.

## 4. Модель доступа

Единственная точка проверки — проект. Задачи, стадии, документы и разделы ИСР уже принадлежат проекту, поэтому отдельного владения у них не появляется.

```text
запрос с project_id  → проверяем членство напрямую
запрос с task_id     → task.project_id → проверяем членство
запрос со stage_id   → stage.project_id → проверяем членство
запрос с document_id → document.project_id → проверяем членство
запрос с link_id     → link.document_id → project_id → проверяем членство
```

**Чужой объект отдаёт 404, а не 403.** Пользователь не должен узнавать, что проект с таким идентификатором вообще существует.

Действия только для владельца: удаление проекта. Всё остальное — задачи, стадии, ИСР, документы, настройки проекта — доступно любому участнику.

Ownership-проверка живёт в сервисном слое, как и остальные инварианты, которые БД выразить не может. Эндпоинты получают `CurrentUserDep` и передают `user_id` в сервис.

## 5. Backend

### Новые файлы

```text
src/utils/security.py             hash_password, verify_password

```

### Настройки (`AuthSettings`)

`jwt_secret`, `jwt_algorithm` (`HS256`), `access_token_ttl_hours`, `registration_invite_code`, `cookie_name`, `cookie_secure`. Секрет обязателен и читается из `.env` — значения по умолчанию для него не будет, иначе прод рискует уехать с дефолтным ключом.

### Эндпоинты

| Метод | Маршрут | Назначение |
|---|---|---|
| `POST` | `/auth/register` | Регистрация: логин, пароль дважды, ФИО, код приглашения |
| `POST` | `/auth/login` | Вход, ставит httpOnly cookie |
| `POST` | `/auth/logout` | Сброс cookie |
| `GET` | `/auth/me` | Текущий пользователь; 401, если не вошёл |
| `PATCH` | `/users/me` | Профиль: ФИО и контакты |
| `POST` | `/users/me/password` | Смена пароля: текущий + новый дважды |
| `POST` | `/users/me/avatar` | Загрузка фотографии |
| `DELETE` | `/users/me/avatar` | Удаление фотографии |
| `GET` | `/users/me/avatar` | Выдача файла фотографии |

Пароль дважды проверяется и на клиенте, и в Pydantic-схеме: клиент даёт быстрый отклик, сервер — гарантию.

### Закрытие существующего API

`CurrentUserDep` добавляется во все роутеры: `dashboard`, `projects`, `project_stages`, `tasks`, `wbs_nodes`, `documents`, `document_links`, `task_comments`, `task_activity`, `task_attachments`. Сервисы получают `user_id` и проверяют членство. `GET /dashboard` начинает считать портфель только по проектам пользователя.

Открытыми остаются лишь `/auth/register`, `/auth/login`, `/docs` и `/openapi.json`.

### Фотография

Переиспользуем подход `TaskAttachmentStorage`: отдельный адаптер `AvatarStorage` с каталогом `uploads/avatars/<user_id>/`. Ограничения: только растровые изображения, до 5 МБ, одна фотография на пользователя — новая заменяет старую.

### Миграция

Одна миграция: создаёт `users` и `project_members`, удаляет существующие проекты (демо-данные) и добавляет `projects.owner_id` как `NOT NULL`. Порядок именно такой, иначе `NOT NULL` не встанет на непустую таблицу.

### Новые файлы


### Как закрывается интерфейс

`AuthGuard` оборачивает всё приложение: пока `GET /auth/me` не ответил — скелетон, при 401 — редирект на `/login` с запоминанием адреса. Страницы входа и регистрации живут вне guard.

В `lib/api.ts` добавляется `credentials: "include"` и общая обработка 401: сбрасываем кэш пользователя и уводим на вход. Это важно для случая, когда токен протух в открытой вкладке.

Формы регистрации и входа собираются из существующих `Field`, `Input`, `Button` — новых примитивов не требуется. Совпадение паролей проверяется до отправки.

Профиль: ФИО тремя полями, контакты, загрузка фотографии с превью. Аватар и имя появляются внизу сайдбара, оттуда же выход.

## 7. Безопасность

Что делаем осознанно:

- пароль хранится только как bcrypt-хеш; в API он не возвращается никогда;
- ответ на неудачный вход одинаков для «нет такого логина» и «неверный пароль» — иначе логины можно перебирать;
- cookie `httpOnly`, `SameSite=Lax`, `Secure` управляется настройкой (в проде за TLS — включён);
- `SameSite=Lax` закрывает CSRF для наших запросов: все мутации идут методами `POST`/`PATCH`/`DELETE`, которые браузер не отправляет кросс-сайтово;
- CORS уже ограничен списком origin-ов, добавляется `allow_credentials=True`;
- чужой объект — 404, чтобы не подтверждать его существование;
- код приглашения сравнивается с постоянным временем сравнения, чтобы его нельзя было подобрать по времени ответа.

Чего сознательно НЕ делаем в этом заходе: refresh-токенов, блок-листа токенов, ограничения частоты попыток входа, восстановления пароля. Для личного сервиса за кодом приглашения это избыточно; когда появятся другие пользователи — вернёмся.

## 8. Тесты

Backend, по существующей пирамиде:

- `tests/unit/services/test_auth_service.py` — регистрация с неверным кодом, занятый логин, несовпадение паролей, вход с неверным паролем, неактивный пользователь;
- `tests/unit/services/test_users_service.py` — обновление профиля, смена пароля, замена фотографии;
- обновление `test_projects_service.py` и остальных: проверка, что чужой проект не виден и не правится;
- `tests/api/endpoints/test_auth.py` — cookie ставится и сбрасывается, `/auth/me` без cookie отдаёт 401;
- `tests/api/endpoints/test_access_control.py` — закрытые эндпоинты без входа отдают 401;
- `tests/integration/repositories/test_users_repository.py` — уникальность логина, каскад удаления пользователя.

Frontend: валидация формы регистрации (совпадение паролей, обязательные поля) как чистая функция.

Отдельно — сквозная проверка в браузере: регистрация, выход, вход, невидимость чужих проектов, загрузка фотографии.
